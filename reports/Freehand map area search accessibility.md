# Build the list before the lasso

A finger-traced "なぞる" search can stay a touch-and-mouse gesture, but the area search it performs must not depend on that gesture. WCAG 2.2 exempts freehand drawing from its keyboard rule only when the *underlying function* needs a path. "Restrict results to an area" does not need one: vertices, a centre and radius, the viewport or a list of stations and wards all define it fully. SC 2.1.1 (Keyboard), 2.5.1 (Pointer Gestures) and 2.5.7 (Dragging Movements) therefore require a route to the same results, on the same page, that works by keyboard and by single taps. The libraries supply little of that route. Google Maps JS gives you a focusable map with arrow-key panning and turns clickable Advanced Markers into named buttons, but its polygons, circles, editable vertices and boundary layers are unreachable by keyboard and invisible to screen readers. Terra Draw adds only Escape-to-cancel and Enter-to-finish, markerclusterer names clusters in fixed English through a deprecated listener, and vis.gl adds no ARIA of its own. The team therefore builds most of the accessibility layer itself: a text result list as the primary route, one polite status region for counts, a text summary of the active area, two-tone outlines that hold 3:1 contrast over any tile, and a centre-crosshair vertex mode with visible pan and "add point" buttons. DEFRA's open-source map component has already proven that crosshair mode, and it is the only route for voice-control and switch users, who cannot trace a closed path at all. In Japan none of this is yet a legal mandate for a private property site. JIS X 8341-3:2016 (equivalent to WCAG 2.0) is still in force, its WCAG 2.2-identical revision was unpublished as of 29 October 2026, and website accessibility falls under 環境の整備 (advance environmental improvement), which is only a duty to make efforts. Since April 2024, however, businesses must provide 合理的配慮 (reasonable accommodation) when a disabled user asks, and alternatives built in advance are the cheapest way to meet that duty. Build to WCAG 2.2 AA now, because that target also covers the coming JIS, the WCAG 2.1 AA standard US courts apply, and the EU's EN 301 549.

## WCAG exempts the finger stroke, not the area search

The deciding text is a note to SC 2.1.1 Keyboard (Level A). The criterion exempts functions whose "underlying function requires input that depends on the path of the user's movement and not just the endpoints", and W3C names "free hand drawing" as such input. But Note 1 says **"This exception relates to the underlying function, not the input technique"**: handwriting is path-dependent, yet the text entry it performs is not ([Understanding 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)). なぞる splits the same way. Tracing is the technique, and restricting the search to an area is the function. An area is fully defined by endpoints: vertices, a centre and radius, viewport corners, or a set of wards. The gesture may therefore stay pointer-only, but the search must also be keyboard-operable.

Touch input follows the same logic. SC 2.5.1 Pointer Gestures (A) requires that path-based gestures "can be operated with a single pointer without a path-based gesture, unless a multipoint or path-based gesture is essential". W3C's sufficient technique G215 is "Providing controls to achieve the same result as path based or multipoint gestures", and failure F105 describes this exact case: "providing functionality via a path-based gesture without simple pointer alternative" ([Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)). The same page's map example accepts plus/minus buttons as the alternative to pinch-zoom. SC 2.5.7 Dragging Movements (AA, new in 2.2) adds a separate dragging rule. Its examples are a draggable map that also has up/down/left/right buttons, and a drag-drawn selection rectangle whose alternative is to set one corner and then the other ([Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)). Tap-to-place polygon vertices are that rectangle generalised to more corners.

Two details in 2.5.7 shape the design. First, **a keyboard equivalent does not satisfy 2.5.7 "unless that equivalent keyboard operation also provides controls that can be clicked or tapped with a pointer."** Arrow keys inside the map pass 2.1.1 but fail 2.5.7, so the keyboard route and the single-pointer route should be the same visible buttons. Second, the single-pointer alternative "can't exclusively rely on a path-based gesture, such as swiping", so a radius that can only be set by dragging a handle also fails (same source).

Completing a stroke when the finger lifts is allowed. SC 2.5.2 Pointer Cancellation (A) accepts completion "on the up-event" if "a mechanism is available to abort the function before completion or to undo the function after completion" ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). Its techniques are G210 (drag-and-drop actions that can be cancelled) and G212 (native controls that fire on the up-event); failure F101 is activating a control on the down-event ([Understanding 2.5.2](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)). For なぞる this has four consequences. Escape or a `pointercancel` event must abort a stroke mid-trace. Tiny strokes and strokes released off the map should be discarded. A visible クリア (clear) or 元に戻す (undo) button must restore the previous area and its results. And the trace toggle must be a native button that fires on click. SC 2.1.2 No Keyboard Trap (A) then requires that drawing mode can always be left by keyboard. If leaving needs more than "unmodified arrow or tab keys or other standard exit methods", the user must be "advised of the method" ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)).

### The perceivable criteria depend on what the map means

SC 1.1.1 requires that a control "has a name that describes its purpose" ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). What a search map conveys is which properties match and where they are. Its text alternative is therefore the result list plus a summary such as 「描いたエリア内：349件」 ("349 results inside the drawn area"), not a prose description of tiles.

SC 1.4.11 requires 3:1 for graphical objects needed to understand the content. Where colours vary, the Understanding document says to test "the least contrasting area" ([Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). A drawn outline crosses white roads, green parks, blue water and dark-mode tiles, so no single stroke colour passes everywhere. A dark stroke with a light halo does.

SC 1.4.3 needs 4.5:1 for cluster count digits, relaxed to 3:1 only for large-scale text of 18 pt, or 14 pt bold. Its exemption for text "part of a picture that contains significant other visual content" covers Google's street labels ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)).

SC 1.4.10 Reflow names maps as content that needs two-dimensional layout, but the exemption "does not automatically extend" to toolbars, search fields and lists around the map ([Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

SC 2.5.8 accepts crowded pins under its Essential exception because "it is essential to show the pins at the correct map location", but W3C "strongly encourage[s]" an equivalent alternative, which here is the list ([Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)).

SC 2.4.11 hits mobile layouts hardest. Its Understanding document names "sticky footers, sticky headers, and non-modal dialogs" as the usual culprits. For panels the user can move, it assesses "only the starting position", so a results bottom sheet must not fully cover a focused cluster in its initial position. The fix is technique C43, CSS scroll-padding; the matching failure is F110 ([Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)).

### The understandable and robust criteria govern auto-search, errors and shortcuts

Auto-searching when the finger lifts changes content rather than context, so SC 3.2.2 On Input allows it, as long as lifting the finger does not also switch to the list view or move focus. Those changes need prior warning or an explicit button. The count change is a status message under SC 4.1.3, so screen readers must receive it without focus moving ([Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)).

Invalid shapes are input errors under SC 3.3.1 and 3.3.3. The response should name the problem and suggest a fix, for example 「範囲が狭すぎます。もう少し大きく囲むか、駅・エリアから探してください」 ("The area is too small. Circle a larger area, or search by station or area"). Silently discarding the stroke fails 3.3.1.

Two less obvious criteria govern keyboard and voice input. SC 2.1.4 Character Key Shortcuts permits single-letter shortcuts only if they can be turned off, can be remapped, or are "only active when that component has focus" ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). That rules out the page-wide F/C/Z drawing keys some GIS tools use. SC 2.5.3 Label in Name requires the accessible name to contain the visible text, which is what lets a voice user say "タップ 完了" ("tap Done").

W3C has no normative map guideline. Maps appear only as examples in the Understanding documents for 1.4.10, 2.5.1, 2.5.7 and 2.5.8. The 2020 W3C/OGC "Maps for the Web" workshop listed "real-world-feature-based accessibility" among its requirements and recommended a working group ([Workshop report](https://www.w3.org/2020/maps/report)). The WAI research wiki page on accessible maps "does not necessarily represent consensus" ([WAI RD wiki](https://www.w3.org/WAI/RD/wiki/Accessible_Maps.html)). Auditors therefore apply the general criteria above and expect an equivalent path that does not need the map.

## Google's map is keyboard-ready, but every drawn shape is invisible

Google Maps JS gives the base map more accessibility than its documentation suggests. Everything in this paragraph comes from reading the minified 3.66.12d weekly build, so it describes that build only. The focusable map container gets `role="region"`, `aria-roledescription="map"` and a hard-coded `aria-label="Map"`. It takes `tabIndex=0` unless `keyboardShortcuts` is false ([common.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/common.js); [map.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/map.js)). Once the map has focus, arrows pan, +/− zoom, Home/End/PageUp/PageDown jump 75% of the view, and Shift+arrows rotate or tilt where those are enabled. A "Keyboard shortcuts" button opens a dialog that lists all of these ([util.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/util.js)).

**`gestureHandling: 'none'` does not disable keyboard pan or zoom; only `keyboardShortcuts: false` does.** The keyboard handler reads the `keyboardShortcuts` flag and never consults `gestureHandling` ([controls.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/controls.js)), even though the reference describes `none` only as "the map cannot be panned or zoomed by user gestures" ([Map reference](https://developers.google.com/maps/documentation/javascript/reference/map)). That cuts both ways for なぞる. Trace mode can freeze touch panning while keyboard users keep panning, which is exactly what a crosshair mode needs. But trace-mode recipes that also set `keyboardShortcuts: false`, including the implementation sketch in our earlier research, remove the map from the Tab order and switch off keyboard panning. Drop that option.

Three more source-level details matter. With `gestureHandling: 'none'` the API removes its hidden touch-navigation sentence ("double-tap and hold your finger on the map, then drag the map"), so trace mode must supply its own instructions ([map.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/map.js)). The keyboard handler ignores events whose target is not the map container itself, so arrows stop panning if focus sits on a custom drawing overlay. MapOptions has no accessible-name or description option, and I could not verify whether the "Map" label is localized under `language=ja`.

Google publishes Accessibility Conformance Reports for Workspace, Chrome, Cloud and Pixel, but **none for Maps Platform** ([Google ACRs](https://accessibility.google/accessibility-conformance-reports)). A buyer who requires an ACR will get one only if the team writes it.

Markers are the best-supported piece. An `AdvancedMarkerElement` with `gmpClickable: true` becomes interactive "for accessibility purposes (e.g. allowing keyboard navigation via arrow keys)", and its `title` becomes the screen-reader text ([AdvancedMarkerElement reference](https://developers.google.com/maps/documentation/javascript/reference/advanced-markers)). Google's guide sets out the model: Tab reaches the first marker, arrow keys cycle through the rest, Enter "clicks", and an info window returns focus to its marker when it closes. The guide adds that "default markers meet the WCAG AA minimum size standard" ([accessible markers guide](https://developers.google.com/maps/documentation/javascript/advanced-markers/accessible-markers)). In code, an interactive marker gets `role="button"`, a non-interactive marker with a `title` gets `role="img"`, and focus on a child element is rejected with "Focusable child elements in AdvancedMarkerElement are not supported" ([marker.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/marker.js)). Google, not the app, controls the arrow-key order, so with hundreds of pins a keyboard user steps through every one. That alone makes a list necessary.

The marker API is still changing. Google deprecated `addListener()` on Advanced Markers in 3.66.4d (September 2026). It then fixed arrow keys moving focus to off-screen markers in 3.66.8b (8 October), and InfoWindows that did not close on Escape or return focus in 3.66.9d (14 October) ([release notes](https://developers.google.com/maps/documentation/javascript/releases)). Pin a tested minor version for accessibility QA rather than loading `weekly`.

Shapes get nothing. The `poly` module that renders `Polygon`, `Circle` and `Polyline` contains no `tabindex`, no focus handling, no `keydown` handler and no role. Its only ARIA is the "Undo last edit" button shown while a shape is being edited ([poly.js](https://maps.googleapis.com/maps-api-v3/api/js/66/12d/poly.js)). Editable vertices can only be dragged with a pointer. Data-driven-styling boundary layers (wards, postal codes) are documented only for `click` and `mousemove`, with no mention of keyboard or screen readers ([DDS handle events](https://developers.google.com/maps/documentation/javascript/dds-boundaries/handle-events)). A drawn area, a radius circle, an isochrone polygon and a tapped ward boundary are therefore all invisible to assistive technology until the app describes them in text.

### The add-on libraries contribute two keys and a title prop

Terra Draw (1.39.0, with Google adapter 1.7.0) gives freehand and polygon modes a default of `{cancel: Escape, finish: Enter}`. Freehand's Enter finishes only when the shape can close, and no key adds a polygon vertex ([freehand.mode.ts](https://github.com/JamesLMilner/terra-draw/blob/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/packages/terra-draw/src/modes/freehand/freehand.mode.ts); [polygon.mode.ts](https://github.com/JamesLMilner/terra-draw/blob/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/packages/terra-draw/src/modes/polygon/polygon.mode.ts)). Select mode binds Ctrl+R and Ctrl+S to rotate and scale ([select.mode.ts](https://github.com/JamesLMilner/terra-draw/blob/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/packages/terra-draw/src/modes/select/select.mode.ts)). Those collide with the browser's reload and save, so remap or disable them. Neither the core nor the adapter source contains any `aria-` attribute, `tabindex`, role or `.focus(` call ([source tree](https://github.com/JamesLMilner/terra-draw/tree/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/packages)), and no accessibility issue has been filed. The Google adapter listens for keys on `map.getDiv()`. Those keys only began arriving once adapter 1.1.2 (December 2025) fixed "keyboard events not firing when map is focused" ([issue #703](https://github.com/JamesLMilner/terra-draw/issues/703); [CHANGELOG](https://github.com/JamesLMilner/terra-draw/blob/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/packages/terra-draw-google-maps-adapter/CHANGELOG.md)). The guide's line "All modes work with keyboard and mouse interface" means shortcuts alongside a mouse, not keyboard-only drawing ([4.MODES.md](https://github.com/JamesLMilner/terra-draw/blob/4a8cfa2ef2dece2284dd06aa71ed0023d84a5cfb/guides/4.MODES.md)).

@googlemaps/markerclusterer's default renderer returns an `AdvancedMarkerElement` titled `Cluster of ${count} markers`, without `gmpClickable` ([renderer.ts](https://github.com/googlemaps/js-markerclusterer/blob/3a887f2031b27f9c9a538274630e969090740025/src/renderer.ts)). Clusters become focusable buttons only because the library calls the now-deprecated `addListener('gmp-click')` for its default zoom-to-bounds handler ([markerclusterer.ts](https://github.com/googlemaps/js-markerclusterer/blob/3a887f2031b27f9c9a538274630e969090740025/src/markerclusterer.ts)). The npm package has not been released since 2.6.2 in July 2025 ([releases](https://github.com/googlemaps/js-markerclusterer/releases)). An open issue reports that switching to `addEventListener` without `gmpClickable` stops clicks firing ([#1152](https://github.com/googlemaps/js-markerclusterer/issues/1152)). Pressing Enter on a cluster runs `fitBounds` and recreates every marker, so focus is likely lost and nothing announces the new view. I have not tested this in a browser.

@vis.gl/react-google-maps (1.10.1) passes `title` through. It turns `clickable` on automatically when `onClick`, `onKeyDown`, `onKeyUp` or the mouse-enter/leave handlers are set ([advanced-marker.tsx](https://github.com/visgl/react-google-maps/blob/b9734e5f9ed12dc30281d1d7fae89272a69b6adb/src/components/advanced-marker.tsx)). The keyboard props arrived in v1.9.0 (June 2026), answering a request filed "for better accessibility" ([CHANGELOG](https://github.com/visgl/react-google-maps/blob/b9734e5f9ed12dc30281d1d7fae89272a69b6adb/CHANGELOG.md); [#923](https://github.com/visgl/react-google-maps/issues/923)). The `Map` component has no ARIA props ([map/index.tsx](https://github.com/visgl/react-google-maps/blob/b9734e5f9ed12dc30281d1d7fae89272a69b6adb/src/components/map/index.tsx)), and there are still no polygon components ([#435](https://github.com/visgl/react-google-maps/issues/435)). The official clustering example renders `<AdvancedMarker onClick>` without a `title` ([tree-marker.tsx](https://github.com/visgl/react-google-maps/blob/b9734e5f9ed12dc30281d1d7fae89272a69b6adb/examples/marker-clustering/src/tree-marker.tsx)), so copying it produces unnamed buttons.

## A centre crosshair gives keyboard, voice and switch users one path

### DEFRA's draw plugin is the prior art to copy

The most complete open-source answer to "draw a polygon without a pointer" comes from the UK Department for Environment, Food & Rural Affairs. Its MIT-licensed `interactive-map` calls itself an "Accessibility-first interactive map component" ([DEFRA/interactive-map](https://github.com/DEFRA/interactive-map)). The draw plugin's model is simple: "While drawing, a crosshair marks where the next point is placed… Keyboard users get the crosshair and press Enter to add a point." On touch the same crosshair appears with an Add point button ([draw.md](https://github.com/DEFRA/interactive-map/blob/main/docs/plugins/draw.md)). Validation is built in. A polygon needs three vertices, and a vertex that would make the path cross itself "is rejected and never placed". While a rule fails, the shape gets a dashed outline, a cue that does not depend on colour. Apps can override the message screen readers hear. Two caveats apply: the component runs on MapLibre and OpenLayers, not Google Maps, and it is at v0.0.58-alpha, described by Defra as "currently in beta and not yet stable" ([Defra accessible maps](https://digital.defra.gov.uk/architecture-and-software-development/defra-accessible-maps)). Copy the pattern and the key bindings, not the code.

| Key or button | Action |
|---|---|
| Enter | Add a point (drawing) |
| Space | Select the nearest point (editing) |
| Alt+arrows | Move to the adjacent point |
| Arrows / Shift+arrows | Move / nudge the selected point |
| Delete | Delete the point |
| Cmd/Ctrl+Z | Undo |
| Toolbar | Cancel, Add point, Done, Undo, Snap, Delete point |

The mainstream drawing libraries mostly lack this. **Esri's Sketch widget and Azure Maps** both bind F to "add vertex", but they place the vertex at the *mouse pointer*, and Azure adds it only "if the mouse is over the map" ([Azure Maps](https://learn.microsoft.com/en-us/azure/azure-maps/drawing-tools-interactions-keyboard-shortcuts); [Esri Sketch](https://developers.arcgis.com/javascript/latest/references/core/widgets/Sketch/)). That helps a mouse user with tremor but gives a keyboard user nothing. Esri staff concede that vertex editing is "not very keyboard accessible with our API at the moment" ([Esri Community](https://community.esri.com/t5/accessibility-questions/sketch-tool-keyboard-commands/m-p/1242457/highlight/true)). **Mapbox GL Draw** has had an issue titled "Accessibility: No keyboard support for drawing shapes" open since June 2025 ([#1410](https://github.com/mapbox/mapbox-gl-draw/issues/1410)). **Leaflet.draw** has had an issue open since 2019 that asks for exactly the crosshair: "start using the centre point of the view-port then use arrow navigation to pan. The next time I hit enter a new point is added" ([#925](https://github.com/Leaflet/Leaflet.draw/issues/925)). **Leaflet-Geoman** added only Escape-to-exit and Enter-to-finish, and both are off by default ([PR #1612](https://github.com/geoman-io/leaflet-geoman/pull/1612)).

The cost shows up in real services. The UK Environment Agency's "Flood map for planning" asks users to draw a site boundary. Tested against WCAG 2.2 AA in March 2025, it lists known failures of 2.1.1 ("boundary reshaping works only with a mouse") and 2.5.7 ("boundary reshaping requires dragging") ([accessibility statement](https://flood-map-for-planning.service.gov.uk/accessibility-statement)).

On Google Maps the crosshair is a small build, because Google's own handler already pans with the arrow keys. Keep focus on the map container, draw a CSS crosshair at the viewport centre, and append `map.getCenter()` when the user presses Enter:

```ts
// Untested sketch: crosshair polygon mode on Maps JS (keyboard, voice, switch)
const vertices: google.maps.LatLng[] = [];
const draft = new google.maps.Polyline({ map, clickable: false, path: vertices });

function addVertex() {                       // Enter on the map, or the 「頂点を追加」 button
  vertices.push(map.getCenter()!);
  draft.setPath(vertices);
  announce(vertices.length >= 3
    ? `頂点${vertices.length}を追加。「完了」で範囲を確定できます`
    : `頂点${vertices.length}を追加。あと${3 - vertices.length}点必要です`);
}
function undoVertex() { vertices.pop(); draft.setPath(vertices); announce(`頂点を削除。残り${vertices.length}点`); }

map.getDiv().addEventListener('keydown', (e) => {
  if (!crosshairMode) return;
  if ((e.target as HTMLElement).closest('button, a, input, select')) return; // let real controls work
  if (e.key === 'Enter') { e.preventDefault(); addVertex(); }
  else if (e.key === 'Backspace' || ((e.ctrlKey || e.metaKey) && e.key === 'z')) { e.preventDefault(); undoVertex(); }
  else if (e.key === 'Escape') { e.preventDefault(); cancelCrosshair(); } // restore previous area, refocus toggle
});
// Arrows and +/- stay with Google's handler. Hide or un-click markers in this mode so
// arrow keys don't start cycling through them.
```

Pair the keys with visible buttons for 頂点を追加 (add point), 元に戻す (undo), 完了 (done) and キャンセル (cancel), plus a four-way pan pad. Without those buttons the mode passes 2.1.1 but fails 2.5.7. The same buttons also serve screen-reader users in browse mode, voice users and switch users. Avoid bare letter keys: they break 2.1.4 unless scoped to focus, and they collide with screen-reader quick-navigation keys.

The same crosshair can also set the centre for radius and isochrone searches (「ここを中心にする」, "centre here"), so one mechanism covers three alternatives. Terra Draw cannot do any of this, so build the crosshair yourself and feed its polygon into the same pipeline as the trace.

### Screen readers need a labelled map, one status region and a list

Government design systems converge on one model: the map is a visual layer over a complete text route. The UK Hydrographic Office's Admiralty design system says "Every map action … must also be available from the panel or sidebar". It advises `role="application"` only "if you manage keyboard behaviour inside the map", and a labelled region otherwise ([Admiralty: Find a location](https://designsystem.admiralty.co.uk/patterns/find-a-location)). DEFRA's viewport owns every key, so it uses `role="application"` with an `aria-label`, `aria-describedby` instructions and `aria-controls` pointing at a "spatial list". It hides the rendered map with `aria-hidden` and announces through a `role="status"` element ([Viewport.jsx](https://github.com/DEFRA/interactive-map/blob/main/src/App/components/Viewport/Viewport.jsx)). Its labelling advice fits a property map: "Describe what the map shows or what it's for, not where it is. Users can move the map" ([api.md](https://github.com/DEFRA/interactive-map/blob/main/docs/api.md)).

Google Maps forces a different trade-off, because clickable markers and clusters live inside the map's DOM. Applying `aria-hidden` to the map, as DEFRA does, would leave focusable buttons hidden from screen readers, which is itself a defect. The practical setup leaves Google's region and named cluster buttons exposed. Wrap the map in a section headed 「物件地図（描いた範囲の物件を表示）」 ("property map, showing listings in the drawn area"), point `aria-describedby` at Japanese instructions, and add a skip link to 「検索結果一覧（349件）」 ("result list, 349 listings").

One behaviour needs early testing. Screen readers in browse mode capture arrow keys for their reading cursor, so a blind user who Tabs onto Google's `role="region"` map may not be able to pan it. No published test of Google Maps under either role exists. The visible pan and add-point buttons are the fallback that works in every mode.

Announce through **one persistent, polite `role="status"` region that is in the DOM from page load**, and debounce it so that only settled states are spoken. Drupal's announcer waits about 200 ms. A WordPress study found 500 ms the most common delay for live search, and 250 ms worse for users with motor disabilities ([Drupal announce.js](https://www.fs.usda.gov/core/misc/announce.js); [WordPress Trac #32720](https://core.trac.wordpress.org/ticket/32720)). Good messages are short and final, such as 「範囲を確定しました。範囲内の物件は210件です」 ("Area set. 210 listings inside it.") or 「地図を移動しました。『このエリアで検索』で再検索できます」 ("Map moved. Use 'Search this area' to search again."). Never announce each pan step. LIFULL HOME'S does the opposite on its line-search page: a `role="alert"` with `aria-live="assertive"` re-announces the hit count on every checkbox tick ([HOME'S line search](https://www.homes.co.jp/chintai/tokyo/line/)), interrupting whatever the user is hearing.

After drawing finishes, keep focus where the user acted and say how to reach the list. Move focus to the results heading only when the user presses a 「結果を見る」 ("view results") button, which keeps the search an in-page update under 3.2.2. After a cluster zoom, catch the clusterer's `clusteringend` event, announce 「拡大しました：12グループ、349件」 ("Zoomed in: 12 groups, 349 listings"), and put focus somewhere predictable.

### List parity is what makes the map optional

The list counts as the accessible equivalent only if it holds exactly what the map shows: every listing inside the drawn area, the same count as the badges, and a way to filter to one cluster. Proxi's map accessibility statement presents such a panel as a complete path for keyboard and screen-reader users, not a fallback ([Proxi](https://learn.proxi.co/en/articles/14185096-proxi-map-feature-accessibility-statement)). DEFRA's SpatialList implements one as a listbox with a roving tabindex, built "to let voice control and screen readers reach and activate each option" ([SpatialList.jsx](https://github.com/DEFRA/interactive-map/blob/main/src/App/components/Viewport/SpatialList.jsx)).

Japanese portals already offer the non-map routes, but their markup quality varies widely. In the server-rendered HTML, **SUUMO's Tokyo line page has 82 checkboxes and no associated labels**. Each line name is a link inside a `<label>` that neither wraps nor points at its checkbox, so screen-reader and voice users meet unnamed checkboxes ([SUUMO 沿線](https://suumo.jp/chintai/tokyo/ensen/)). SUUMO's own ward page gets it right, with a `<label for>` on every checkbox and the count inside it, as in 千代田区 (32718) ([SUUMO エリア](https://suumo.jp/chintai/tokyo/city/)). at home's line page also labels its checkboxes properly ([at home 沿線](https://www.athome.co.jp/chintai/tokyo/line/)). For your own lists, group each line's stations in a `<fieldset>` with the line name as the `<legend>`. Use real labelled checkboxes, add a tri-state "select all stations" parent, keep the count inside the label, and never put a link inside a checkbox label. Station and address autocomplete should follow the current ARIA APG combobox pattern ([APG combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)).

### Voice and switch users cannot trace a closed path at all

Android Voice Access documents point-to-point "Drag [label or number]", grid-based drags, swipes, long-presses and "Pinch in"/"Pinch out", but no command for an arbitrary path ([Google Voice Access commands](https://support.google.com/accessibility/android/answer/6151854?hl=en)). macOS Voice Control likewise supports grid drags such as "Drag 3 to 14" ([Apple Voice Control](https://support.apple.com/en-am/guide/mac-help/mh40719/mac)). Freehand なぞる is therefore effectively unavailable to voice and switch users, and no amount of polish changes that.

DEFRA states the remedy plainly. Its on-screen move, zoom and target controls give "a non-dragging way to operate the map, for anyone who can't perform a drag or pinch gesture (e.g. switch access users) and for voice interfaces such as Voice Control, which can trigger a button click but not a drag". Disabling them "can fail WCAG 2.5.7" ([api.md](https://github.com/DEFRA/interactive-map/blob/main/docs/api.md)). Every control also needs a visible text label that matches its accessible name, so a user can say "タップ 頂点を追加" ("tap Add point") instead of falling back on "show numbers". The icon-only finger buttons common on Japanese portals fail this practical test even when they carry an `aria-label`. No user research on voice or switch users drawing map polygons was found, so plan to observe a few sessions.

### Low vision and tremor break on contrast, colour and precision

The Flood map for planning audit names the failures to expect. Flood zones and keyboard focus were distinguished by colour alone (1.4.1). The key panel needed two-dimensional scrolling when magnified (1.4.10). The "black target selector against 'Flood zone 3'" lacked contrast (1.4.11) ([accessibility statement](https://flood-map-for-planning.service.gov.uk/accessibility-statement)). Defra's answer was hatched fills, so areas differ without colour, plus a thick yellow focus outline ([Defra Digital blog](https://defradigital.blog.gov.uk/2021/05/20/designing-a-more-accessible-flood-map)). DEFRA's draw plugin adds a halo behind vertex handles and a dashed stroke for invalid shapes ([draw.md](https://github.com/DEFRA/interactive-map/blob/main/docs/plugins/draw.md)). For なぞる, that means a stroke of at least 3 px in a dark colour with a white casing, dashed while drawing and solid once confirmed. Dim everything outside the area rather than tinting the inside, and put a dark ring around cluster badges.

Forced colours and reduced motion need explicit handling. Under Windows forced colours, browsers override author SVG fill and stroke ([MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)). HTML overlays such as the crosshair, toolbar and badges will be recoloured; canvas tiles will not. Test that the crosshair and outline stay visible, and reserve `forced-color-adjust: none` for small elements that need it. Esri's SDK (since 4.30) and MapLibre honour `prefers-reduced-motion` natively ([Esri blog](https://www.esri.com/arcgis-blog/products/js-api-arcgis/mapping/supporting-reduced-motion-enhancing-accessibility-in-web-apps); [MapLibre AnimationOptions](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/AnimationOptions)). No equivalent was found for Google Maps JS, so check the media query yourself and prefer `setCenter`/`setZoom` over an animated `panTo` when reduced motion is set. At 400% zoom (320 CSS px), collapse to one column with a 地図／リスト (map/list) toggle. The 1.4.10 exemption covers only the map, so the trace toolbar must stay in view next to it.

Motor impairments favour the same crosshair. Defra found that people with Parkinson's or arthritis "can find it difficult to use a mouse and often prefer to use a keyboard" ([Defra Digital blog](https://defradigital.blog.gov.uk/2021/05/20/designing-a-more-accessible-flood-map)). DEFRA and Admiralty both set 44×44 px for map controls, well above the 24 px WCAG floor ([DEFRA interact.md](https://github.com/DEFRA/interactive-map/blob/main/docs/plugins/interact.md); [Admiralty](https://designsystem.admiralty.co.uk/patterns/find-a-location)). For tremor during freehand tracing, sample points by minimum distance (Terra Draw defaults to 20 px), simplify the path and auto-close the ring. Repair or explain self-intersections rather than failing silently. When a new drawing replaces an area, offer a one-tap undo rather than a confirmation dialog. No published research validates the smoothing parameters or the undo-over-confirm choice, so test both.

### Each alternative is accessible only through its own controls

An alternative to the trace satisfies 2.1.1, 2.5.1 and 2.5.7 only if its own controls conform. Each one has its own trap.

| Alternative | Accessible core | Trap | Build |
|---|---|---|---|
| Radius from current location | One native 「現在地から探す」 ("search near my location") button plus a `<select>` or radio group (500 m / 1 km / 2 km) | Dragging an editable `Circle` handle alone fails 2.5.7; denied or timed-out geolocation becomes a silent dead end | Preset radius control; a text error with a suggestion (「位置情報を取得できません。駅名で探す」, "can't get your location; search by station name"); a summary 「現在地から半径1km・52件」 ("within 1 km of you, 52 listings") |
| Radius from a chosen point | Station or address combobox (APG) | Long-press to drop a pin is pointer-only | Combobox plus a crosshair 「ここを中心にする」 ("centre here"); the same radius presets |
| "Search this area" | Explicit button using `getBounds()` | Drag-panning needs a non-drag route (2.5.7); auto-refresh on every pan floods the status region; users miss that results are limited to the view | Pan pad plus Google's arrow keys; a button rather than auto-refresh ([Yext pattern](https://hitchhikers.yext.com/modules/pgs604-create-locator/07-adv-search-this-area/)); an announcement such as 「表示範囲内：88件」 ("88 listings in view") |
| Tap-to-place vertices | Single taps satisfy 2.5.1/2.5.7, mirroring W3C's two-corner rectangle | Taps on the map are not keyboard-operable; Google's editable vertices are drag-only | Crosshair with Enter and an add-point button; handles of at least 24 px; select-and-nudge or undo instead of vertex dragging |
| Station / ward / line lists | The most accessible option natively | Unlabelled checkboxes; boundary layers that only respond to clicks | `fieldset`/`legend`, labelled checkboxes, counts in labels; boundaries only highlight what the list selected |
| Walking-time isochrone | Origin from a station combobox, minutes from a select (5/10/15 min) | The resulting polygon is as invisible as a drawn one | A text summary 「渋谷駅から徒歩10分圏・134件」 ("10-minute walk from Shibuya Station, 134 listings"); Google's Isochrones API is still in Preview and has no transit mode ([Isochrones FAQ](https://developers.google.com/maps/documentation/isochrones/faq)) |

## Japan requires accommodation on request, not WCAG conformance — yet

**JIS X 8341-3:2016**, published 22 March 2016 and identical to ISO/IEC 40500:2012 (WCAG 2.0), remains Japan's web accessibility standard ([issoh.co.jp](https://www.issoh.co.jp/column/details/3022/)). A drafting committee formed in October 2025 to adopt ISO/IEC 40500:2025, which is WCAG 2.2, as an identical standard. In January 2026 it expected publication during the year ([gihyo.jp](https://gihyo.jp/article/2026/01/web-accessibility-prospect)). A March 2026 conference deck projected "早ければ2026年10月、遅くとも2027年3月" ("as early as October 2026, March 2027 at the latest") ([Speaker Deck](https://speakerdeck.com/securecat/gai-zheng-jiswojian-ju-eta-qi-ye-noakusesibiriteidui-ying-rodomatupu)). An article updated 12 October 2026 still described the revision as unpublished ([issoh.co.jp](https://www.issoh.co.jp/md/column/7575)), and the Cabinet Office's September 2026 accessibility test still cites the 2016 edition ([内閣府](https://www5.cao.go.jp/j-j/sekai_chouryuu/sh26-01/webaccessibility.html)). Publication by 29 October 2026 could not be confirmed; check JISC or the 官報 (official gazette) directly.

The current JIS already constrains なぞる. SC 2.1.1 and its underlying-function note have been in WCAG since 2.0, so a trace-only search fails even the 2016 JIS. The criteria this feature stresses most are 2.5.1, 2.5.7, 2.5.8, 2.4.11, 1.4.11 and 4.1.3. All of them postdate WCAG 2.0, so they enter Japanese conformance only with the revised JIS. Japanese enterprises already audit some of them. JR東日本 (JR East), for example, publishes per-page results for SC 2.5.7 using technique G219 ([JR東日本](https://www.jreast.co.jp/web_accessibility/2025/03/39/2.5.7.html)). Conformance claims follow WAIC's 対応度表記ガイドライン (guideline on how to state conformance levels) ([WAIC](https://waic.jp/)).

The law draws a sharper line than the standard. Under the amended 障害者差別解消法 (Act on the Elimination of Disability Discrimination), **reasonable accommodation (合理的配慮) has been mandatory for private businesses since 1 April 2024**, while advance environmental improvement (環境の整備) remains an effort duty ([内閣府](https://www8.cao.go.jp/shougai/suishin/sabekai.html)). Municipal guidance places information accessibility inside 環境の整備. Osaka Prefecture's casebook, for instance, lists adding text-to-speech and text enlargement to a website under that heading ([京都市](https://www.city.kyoto.lg.jp/hokenfukushi/cmsfiles/contents/0000192/192671/jireisyuu-3-1.pdf); [大阪府](https://www.pref.osaka.lg.jp/documents/30751/zirei_kannkyoutosonota.pdf)). Mitsue-Links' 中村直樹 sums up web accessibility under the act as "努力義務にしか過ぎません" ("no more than an effort duty"), and notes that no digital accessibility act has been enacted ([gihyo.jp](https://gihyo.jp/article/2026/01/web-accessibility-prospect)). One government explanation that had called web accessibility 合理的配慮 was later corrected to 環境の整備 ([zenn.dev/ymrl](https://zenn.dev/ymrl/articles/62f90ebcce7637)).

Enforcement runs through the competent minister. For 宅地建物取引業 (real-estate brokerage) that is MLIT, which publishes a sector 対応指針 (implementation guideline) ([MLIT 対応指針](https://www.mlit.go.jp/common/001068263.pdf)). The minister can request reports and give advice, guidance and recommendations. Penalties attach only to failing to report or to reporting falsely ([総務省 regulatory assessment](https://www.soumu.go.jp/main_content/000260162.pdf)). No enforcement action or court case about a private website's accessibility under the act was found.

In practice, suppose a blind or motor-impaired user tells a property portal they cannot use なぞる. That triggers a binding duty to offer an alternative unless doing so is an excessive burden (過重な負担). List, radius and crosshair search built in advance discharge that duty without case-by-case work, and staff-assisted search by phone or email is the fallback. Public-sector sites are expected to meet JIS AA under 総務省's みんなの公共サイト運用ガイドライン (public website operation guideline) ([総務省](https://www.soumu.go.jp/main_sosiki/joho_tsusin/b_free/guideline.html)). デジタル庁's introductory guidebook, folded into the government's standard guidelines in October 2025, has no map-specific content ([デジタル庁](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)).

**United States.** There is still no web regulation under ADA Title III, yet federal website suits reached 3,117 in 2025, up 27%, and courts treat WCAG 2.1 AA as the de facto standard ([Level Access](https://www.levelaccess.com/blog/web-accessibility-lawsuits)). The Justice Department's Title II rule for state and local governments was amended in April 2026. It moves compliance to **26 April 2027** for entities serving 50,000 people or more and to **26 April 2028** for smaller ones, still at WCAG 2.1 AA ([Federal Register](https://www.federalregister.gov/documents/2026/04/20/2026-07663/extension-of-compliance-dates-for-nondiscrimination-on-the-basis-of-disability-accessibility-of-web)).

**European Union.** The European Accessibility Act has applied to e-commerce services, among others, since 28 June 2025 ([European Commission](https://commission.europa.eu/strategy-and-policy/policies/justice-and-fundamental-rights/disability/union-equality-strategy-rights-persons-disabilities-2021-2030/european-accessibility-act_en)). Microenterprises (fewer than 10 staff and no more than €2m turnover) are exempt for services ([e-include](https://e-include.eu/web-accessibility/european-accessibility-act/)). EN 301 549, which incorporates WCAG 2.1 AA, is the technical reference ([koksal.av.tr](https://koksal.av.tr/en/legislation/eu-accessibility-act-eaa-germanys-bfsg/)). It is unresolved whether a listing portal, where contracts are concluded offline, counts as an "e-commerce service" under the Directive ([Directive 2019/882](https://eur-lex.europa.eu/eli/dir/2019/882/oj/eng)). Both the US and EU regimes reference WCAG 2.1, which lacks 2.5.7, but 2.1.1 and 2.5.1 already force a route that does not need tracing.

## Scanners check the frame around the map; people must test the map

Automated tools cover the HTML around the map well and the map itself poorly. Deque's study of more than 2,000 audits found that axe caught 57% of issues by count. That is a vendor figure, and it measures issue volume, not success criteria ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)). Playwright's own documentation says automated scans catch only some problems ([Playwright](https://playwright.dev/docs/accessibility-testing)). The Flood map audit shows what is left over: tile contrast, drag-only reshaping and a missing instruction on how to reach the map, none of which a DOM scanner can see ([accessibility statement](https://flood-map-for-planning.service.gov.uk/accessibility-statement)).

In CI, run `@axe-core/playwright` against six states: the initial page, drawing mode, a confirmed area with results, the list view, an open cluster preview and a 320 px viewport. Then add the assertions axe cannot make. Check that the `role="status"` element exists at load and reads 「210件」 after a draw, that the なぞる button toggles `aria-pressed`, and that `getByRole('button', { name: /件の物件/ })` finds every cluster. Add a keyboard-only script that Tabs to the map, enters crosshair mode, presses ArrowRight several times and Enter four times, then presses 完了, and assert that a polygon and a count appear. That script is the regression guard for the 2.1.1/2.5.7 alternative. Finally, run screenshot diffs under `page.emulateMedia` with `forced-colors: active` and with `prefers-reduced-motion: reduce` to confirm the crosshair and outline stay visible. DEFRA's repository shows that keyboard handlers, crosshair visibility and the spatial list can all be unit-tested ([DEFRA repo](https://github.com/DEFRA/interactive-map)).

Manual testing is where the map itself gets judged, and the matrix should follow usage. WebAIM's survey #10 (1,539 respondents, early 2024, an uncontrolled sample) put JAWS at 40.5% and NVDA at 37.7% as primary desktop readers. VoiceOver led on mobile at 70.6%, and NVDA led in Asia ([WebAIM #10](https://webaim.org/projects/screenreadersurvey10/)). No current Japanese product-share survey exists. The National Diet Library's 2021 survey of 739 visually impaired users found 37.1% read documents with a screen reader and 64.0% rely on smartphones or tablets ([NDL](https://www.ndl.go.jp/jp/library/supportvisual/questionnaire2021.html)). PC-Talker is described as the top-selling paid Japanese reader, an undated claim not based on a survey ([mobinc.jp](https://mobinc.jp/media/?p=2984)).

| Environment | Why it is in the matrix |
|---|---|
| NVDA (Japanese) + Chrome/Firefox; JAWS + Chrome | Desktop majority; browse vs. focus mode on the map region |
| PC-Talker + Edge/Chrome | Japanese-market reader; no published Google Maps results exist |
| VoiceOver + Safari (macOS, iOS); TalkBack + Chrome | Mobile web, where most Japanese blind users are |
| Keyboard only; Windows forced colours; 200% and 400% zoom | Crosshair mode, focus visibility, overlay contrast, reflow |
| iOS Voice Control, Android Voice Access, iOS Switch Control | The 「頂点を追加」 path and pan pad, since these users cannot trace at all |
| OS reduce-motion on | Cluster zoom and fit-to-area animations |

Script tasks that mirror real searches in every environment. Find listings within 1 km of 渋谷駅 (Shibuya Station), and select stations on the 東横線 (Tōyoko Line) from the list. Draw an area with the crosshair and hear the count, undo a vertex, and cancel a drawing. Replace an area and undo the replacement. Open a cluster and reach its listings in the list, and use 「このエリアで検索」 ("search this area") after panning. Then test with disabled users, as the Scottish Government's map guidance urges ([designsystem.gov.scot](https://designsystem.gov.scot/guidance/maps/building-accessible-maps)). Defra concluded that no single fix works for every map ([Defra Digital blog](https://defradigital.blog.gov.uk/2021/05/20/designing-a-more-accessible-flood-map)). Publish the results in the per-criterion 試験結果 (test results) format JR East uses, since Google supplies no ACR to lean on.

## Recommended architecture: one area model, six producers, one list

Build one area model and make every search mode a producer for it. The same structure keeps backend querying in one place, so accessibility and engineering want the same thing here.

| Layer | Implementation | Criteria it carries |
|---|---|---|
| Area model | One `SearchArea` state: `geometry` (GeoJSON polygon, circle, bbox, admin codes or isochrone), `summary` (Japanese text), `source` (trace / crosshair / radius / viewport / list / isochrone), `previous` (for undo) | 1.1.1, 1.3.1 (summary); 2.5.2 (undo) |
| Six producers | Pointer trace overlay; crosshair polygon; radius from location or chosen point; "search this area" button; station/ward/line lists; walking isochrone | 2.1.1, 2.5.1, 2.5.7 (every non-trace producer is the alternative) |
| Results | The server returns the in-area list and the cluster counts together, so list and badges always agree | 1.1.1 parity; 2.5.8 Equivalent |
| Announcer | One polite `role="status"` region, debounced 300–500 ms after `idle` or draw completion; `role="alert"` for shape errors | 4.1.3, 3.3.1, 3.3.3 |
| Area-mode toolbar | Native `<button>`s with visible Japanese text; なぞる with `aria-pressed`; Done/Undo/Cancel/Add point; pan pad; at least 44 px on touch | 4.1.2, 2.5.3, 2.5.8, 2.1.2, 2.5.7 |
| Map shell | Labelled wrapper section with instructions; skip link to the results heading; Google map with keyboard shortcuts left on | 1.1.1, 2.4.3, 2.1.1 |
| Overlay styling | Dark stroke with a light casing; dashed while drafting; dimmed exterior; ringed badges; forced-colours and reduced-motion queries | 1.4.11, 1.4.1, 1.4.3 |

Library configuration follows from the findings above. In trace mode, set `gestureHandling: 'none'` and `clickableIcons: false` and add a transparent `touch-action: none` overlay. Complete the stroke on `pointerup`, abort it on Escape or `pointercancel`, then restore the previous gesture setting. Never touch `keyboardShortcuts`. If Terra Draw handles desktop freehand, keep its Escape cancel and remap or disable select mode's Ctrl+R and Ctrl+S. Do not count Terra Draw as the keyboard path; the crosshair is that path. In React, give every `<AdvancedMarker>` a localized `title`, and never render buttons or links as marker children ([#704](https://github.com/visgl/react-google-maps/issues/704)). Pin a tested Maps JS minor version, because Google is still changing marker and InfoWindow focus behaviour. For clusters, supply your own renderer so that every cluster gets a Japanese name and `gmpClickable` however the deprecated listener path evolves:

```ts
const renderer = {
  render: ({ count, position }) => new google.maps.marker.AdvancedMarkerElement({
    position,
    gmpClickable: true,                          // focusable role="button", independent of addListener
    title: `${count}件の物件。選択すると拡大します`,   // the accessible name; don't rely on SVG digits
    content: makeBubble(count),                  // visual only: no buttons or links inside
  }),
};
```

On mobile web, three layout rules follow from 2.4.11 and 1.4.10. The draggable results sheet must not cover focused items in its starting position. Below 320 px, map and list become a toggle. The trace toolbar always stays inside the viewport.

Sequence the build around risk. Start with the parts that serve everyone: station, ward and line lists with correct labels, the result list with its heading and count, the status region and the area summary chip. Together these already satisfy 2.1.1 and 2.5.7 for "restrict search to an area". Add radius search and "search this area" with the pan pad next. Then add the crosshair polygon, which gives keyboard, voice and switch users their own way to draw a shape. Ship freehand なぞる last, as the fast path for touch and mouse users on top of a pipeline that is already accessible.

## Conclusion

The accessible version of this feature is not an "accessibility mode" bolted onto the trace. The crosshair, the visible buttons and the list are the universal input path, and freehand tracing is a shortcut for the people who can use it. That reframing moves most of the work out of drawing code and into the area model, the list and the announcer, which the team would want anyway for saved searches, alerts and mobile layouts. The ecosystem's real gap is shapes. Google's polygons, Terra Draw's modes and Google's boundary layers are all unreachable by keyboard and invisible to screen readers. The only mature prior art for keyboard polygon drawing, DEFRA's alpha-stage component, runs on a different map engine, so every Google Maps team building area search is currently solving the same problem from scratch.

Timing makes this urgent in Japan rather than merely good practice. The WCAG 2.2-based JIS is expected within months. It adds 2.5.7, 2.5.8, 2.4.11 and 4.1.3, precisely the criteria that a finger-traced search with clustered badges and a bottom sheet is most likely to fail. Meanwhile, the 2024 合理的配慮 duty already obliges a portal to respond to any user who says they cannot trace. Three questions remain open, and they decide whether the design works for real users or only on paper. First, how do Japanese screen readers (NVDA Japanese and PC-Talker) behave on Google's map region in browse mode? Second, does focus survive a cluster zoom? Third, can voice and switch users complete a crosshair polygon? Test all three in the first sprint.
