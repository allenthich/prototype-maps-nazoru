# Trace-to-search works everywhere except Google Places

You can build a finger-traced "なぞる" search area today on web, Android, iOS, React Native and Flutter. No Google SDK ships it, though. On every platform you assemble it from the same four primitives: pause map panning, capture the finger on an overlay, convert screen points to lat/lng through the map's projection, and close the path into a polygon. The web got harder in 2026. Google removed its Drawing Library, which never had a freehand mode anyway, and now points developers to Terra Draw. Terra Draw is a third-party library that Google does not support, and its own docs still list freehand as unsupported on touch devices. The bigger limit is the search behind the map. **Google Places cannot restrict a search to an arbitrary polygon.** Nearby Search accepts only a circle (50 km max radius, 20 results), and Text Search only restricts to a rectangle (60 results max). A lasso over Places data therefore means tiling the area, filtering points client-side, and paying per request ($32 per 1,000 after 5,000 free each month). Only the Places Aggregate API accepts a custom polygon, and it returns counts. It returns Place IDs only when the count is 100 or fewer. Your own data is a different story. SUUMO, LIFULL HOME'S and Canary made なぞって検索 a Japanese convention on top of their own listings, and every mainstream geo index except Firestore filters by polygon exactly. Server-side grid aggregation then produces the count badges. Radius search is the shape Places supports natively, so it is the right default when results come from Google. WCAG 2.2 also effectively requires a non-drawing alternative. The recommended build has six parts: an explicit trace-mode button, one coordinate conversion when the finger lifts, a simplified and validated polygon, a query against your own index, server-side counts, and accessible alternatives (station or ward lists, plus radius or walking-time search).

## Five platforms share one recipe, and none ships it

Google publishes no freehand lasso API or sample on any of its SDKs. The working pattern is the same everywhere. First, disable the map's pan gesture and put a transparent touch-capturing layer over the map. Second, collect finger positions as screen points. Third, convert them to lat/lng with the map's projection. Fourth, render a live stroke and swap it for a polygon when the finger lifts. The most robust version draws the stroke in screen space and **converts to coordinates once, on finger-lift**, not on every move event. István Juhos of Spoke described exactly this production design at DevFest Venezia in October 2026. His design uses a Compose `Canvas` overlay that collects screen offsets and converts them all in `onDragEnd` via `projection.fromScreenLocation` ([Speaker Deck](https://speakerdeck.com/stewemetal/paths-polygons-and-donuts-building-a-freehand-drawing-tool-for-maps-devfest-venezia-2026-edition)). Keep the camera locked for the whole stroke, because the projection used at conversion time must match what the user saw.

| Platform | Pause map panning | Screen point → lat/lng | Point-in-polygon helper | Main trap |
|---|---|---|---|---|
| Web (Maps JS) | `map.setOptions({gestureHandling: 'none'})` plus an overlay with `touch-action: none` | `OverlayView.getProjection().fromContainerPixelToLatLng()` | `geometry.poly.containsLocation`, or Turf `booleanPointInPolygon` | Drawing Library removed; Terra Draw freehand officially unsupported on touch |
| Android (Views / Compose) | `UiSettings.setScrollGesturesEnabled(false)` / `MapUiSettings(scrollGesturesEnabled = false)` | `Projection.fromScreenLocation(Point)` (physical pixels) | `PolyUtil.containsLocation` and `PolyUtil.simplify` | Compose projection is null until the map loads |
| iOS (Google Maps SDK) | `mapView.settings.scrollGestures = false` | `projection.coordinateForPoint:` (points) | `GMSGeometryContainsLocation` | No built-in path simplification |
| iOS (MapKit, for comparison) | `isScrollEnabled = false`; SwiftUI `interactionModes` | `convert(_:toCoordinateFrom:)`; `MapProxy.convert` (iOS 17+) | Renderer path test or your own ray-cast | Not Google Maps, but ports to the Google SDK almost 1:1 |
| React Native (react-native-maps) | `scrollEnabled={false}` | `onPanDrag` delivers native coordinates per event; `coordinateForPoint` returns a Promise | None built in; use Turf | No drag-end event |
| Flutter (google_maps_flutter) | `scrollGesturesEnabled: false` | `await controller.getLatLng(ScreenCoordinate)` | None built in; write a Dart ray-cast | Android expects physical pixels, iOS expects points |

### The web lost its only drawing tool in mid-2026

Google deprecated the Drawing Library in Maps JS 3.62.2c (28 August 2025). Release 3.65.3b (4 June 2026) states that "the DrawingManager functionality … is no longer available" ([release notes](https://developers.google.com/maps/documentation/javascript/releases)). The deprecations page lists it as a completed decommission and names Terra Draw as the example replacement ([Google deprecations](https://developers.google.com/maps/deprecations)). The TypeScript typings still declare the class, so old code compiles but fails at runtime ([@types/google.maps](https://unpkg.com/@types/google.maps@latest/index.d.ts)). Freehand drawing never existed there anyway. `OverlayType` offered only circle, marker, polygon, polyline and rectangle, all drawn by clicking vertices ([@types 3.58.1](https://unpkg.com/@types/google.maps@3.58.1/index.d.ts)). Treat any blog post or Stack Overflow answer that uses `google.maps.drawing` as obsolete.

Terra Draw is the de facto replacement. Google's own sample loads `terra-draw` with `terra-draw-google-maps-adapter` and includes a freehand button. The sample also states that Terra Draw "is not supported by Google" ([Google sample](https://developers.google.com/maps/documentation/javascript/examples/map-drawing-terradraw)). The current versions are `terra-draw` 1.39.0 (28 October 2026) and adapter 1.7.0 ([CHANGELOG](https://github.com/JamesLMilner/terra-draw/blob/main/packages/terra-draw/CHANGELOG.md)). **Since 1.25.0 (February 2026), `TerraDrawFreehandMode` accepts `drawInteraction: 'click-drag'`**, which gives press-drag-release lasso drawing. The docs describe this mode as "touch-friendly" ([modes guide](https://github.com/JamesLMilner/terra-draw/blob/main/guides/4.MODES.md)). The mode also offers `minDistance` (default 20 px), `smoothing` and `autoClose` options ([freehand.mode.ts](https://github.com/JamesLMilner/terra-draw/blob/main/packages/terra-draw/src/modes/freehand/freehand.mode.ts)). The same guide, however, still says "Freehand is not currently supported" on touch devices. A multi-touch PR was closed unmerged after a tester marked one-finger drawing with two-finger pinch as failing on iPhone and iPad Safari ([issue #826](https://github.com/JamesLMilner/terra-draw/issues/826)). A March 2026 request for exactly this feature ("mobile map-based real estate area search") was answered with a pointer to `drawInteraction` and then closed for lack of follow-up ([issue #827](https://github.com/JamesLMilner/terra-draw/issues/827)). There is one more catch. The Google adapter pauses panning by toggling the deprecated `draggable` option rather than `gestureHandling` ([adapter source](https://github.com/JamesLMilner/terra-draw/blob/main/packages/terra-draw-google-maps-adapter/src/terra-draw-google-maps-adapter.ts)), so pinch gestures can leak through mid-stroke unless you also set `gestureHandling: 'none'` yourself. For React, vis.gl ships an official Terra Draw example with a `useTerraDraw` hook ([use-terra-draw.ts](https://github.com/visgl/react-google-maps/blob/main/examples/terra-draw/src/use-terra-draw.ts)).

A custom implementation is short and avoids the touch uncertainty. The key is that the map's default `gestureHandling: 'auto'` becomes `cooperative` on scrollable pages, where "one-finger gestures scroll the page", so a one-finger trace fights page scrolling. `'none'` prevents all pan and zoom gestures ([Map reference](https://developers.google.com/maps/documentation/javascript/reference/map)). Put a transparent overlay with `touch-action: none` over the map. Capture Pointer Events on it and ignore non-primary pointers. Convert points through a no-op `OverlayView`'s `fromContainerPixelToLatLng`, which also handles heading and tilt on vector maps ([OverlayView reference](https://developers.google.com/maps/documentation/javascript/reference/overlay-view)). Then push the points into a `Polyline` path, which redraws live because it is an MVCArray ([Polygon reference](https://developers.google.com/maps/documentation/javascript/reference/polygon)). Set `clickableIcons: false` and hide Advanced Markers during the stroke. Terra Draw's adapter has to forward events from `gmp-advanced-marker` elements and Data-layer features precisely because they swallow pointer events ([adapter source](https://github.com/JamesLMilner/terra-draw/blob/main/packages/terra-draw-google-maps-adapter/src/terra-draw-google-maps-adapter.ts)). deck.gl's lasso-style `DrawPolygonByDraggingMode` is a poor fit on Google Maps, because `GoogleMapsOverlay` does not support drag gesture callbacks ([deck.gl Google Maps](https://deck.gl/docs/api-reference/google-maps/overview)).

```ts
// Untested sketch assembled from documented Maps JS APIs
class Proj extends google.maps.OverlayView { onAdd() {} draw() {} onRemove() {} }
const proj = new Proj(); proj.setMap(map);            // getProjection() is valid after onAdd/draw

function enterTraceMode() {                             // the "なぞる" button
  map.setOptions({ gestureHandling: 'none', clickableIcons: false });
  overlay.style.display = 'block';                      // transparent div over map.getDiv(), CSS touch-action:none
}
overlay.onpointerdown = e => { if (!e.isPrimary) return;
  overlay.setPointerCapture(e.pointerId);
  stroke = new google.maps.Polyline({ map, clickable: false, path: [toLatLng(e)] }); };
overlay.onpointermove = e => stroke?.getPath().push(toLatLng(e));  // add min-distance sampling in practice
overlay.onpointerup = () => { /* simplify → close → CCW → unkink → Polygon → restore gestures → query */ };

const toLatLng = (e: PointerEvent) => { const r = map.getDiv().getBoundingClientRect();
  return proj.getProjection().fromContainerPixelToLatLng(
    new google.maps.Point(e.clientX - r.left, e.clientY - r.top))!; };
```

### Native SDKs need an overlay; bridges add async and unit traps

On **Android**, everything you need is first-party. `setScrollGesturesEnabled(false)` pauses panning ([UiSettings](https://developers.google.com/android/reference/com/google/android/gms/maps/UiSettings)), and Maps Compose exposes the same flags in `MapUiSettings` ([MapUiSettings.kt](https://github.com/googlemaps/android-maps-compose/blob/main/maps-compose/src/main/java/com/google/maps/android/compose/MapUiSettings.kt)). `Projection.fromScreenLocation` converts points ([Projection](https://developers.google.com/android/reference/com/google/android/gms/maps/Projection)), though Compose's `cameraPositionState.projection` stays null until the map loads ([CameraPositionState.kt](https://github.com/googlemaps/android-maps-compose/blob/main/maps-compose/src/main/java/com/google/maps/android/compose/CameraPositionState.kt)). android-maps-utils supplies `PolyUtil.containsLocation`, with a geodesic or rhumb flag, and Douglas-Peucker `PolyUtil.simplify` ([PolyUtil](https://googlemaps.github.io/android-maps-utils/library/com.google.maps.android/-poly-util/index.html)). On **iOS**, the Google SDK mirrors this with `settings.scrollGestures` ([GMSUISettings](https://developers.google.com/maps/documentation/ios-sdk/reference/objc/Classes/GMSUISettings)), `coordinateForPoint:` in points ([GMSProjection](https://developers.google.com/maps/documentation/ios-sdk/reference/objc/Classes/GMSProjection)) and `GMSGeometryContainsLocation`. It documents no simplification function, so you write your own Douglas-Peucker ([GMS functions](https://developers.google.com/maps/documentation/ios-sdk/reference/objc/Functions)). MapKit apps use the same structure with `isScrollEnabled` and `convert(_:toCoordinateFrom:)` ([Apple](https://developer.apple.com/documentation/mapkit/mkmapview/convert%28_:tocoordinatefrom:%29)), or with `MapReader`/`MapProxy.convert` on SwiftUI from iOS 17 ([MapProxy](https://developer.apple.com/documentation/mapkit/mapproxy)). Porting a MapKit trace feature to Google Maps is therefore close to a rename.

**React Native** is the easiest of the cross-platform options. react-native-maps 1.29.11 is actively maintained and supports the New Architecture ([npm](https://www.npmjs.com/package/react-native-maps)). Its official `PolygonCreator` example already implements freehand capture: in edit mode it sets `scrollEnabled = false` and appends `e.nativeEvent.coordinate` from `onPanDrag` ([PolygonCreator.tsx](https://github.com/react-native-maps/react-native-maps/blob/master/example/src/examples/PolygonCreator.tsx)). Because `onPanDrag` delivers natively computed coordinates, you avoid a Promise round-trip per point through `coordinateForPoint` ([mapview.md](https://github.com/react-native-maps/react-native-maps/blob/master/docs/mapview.md)). On Android the event comes from a `GestureDetector` on the wrapper view, so it keeps firing with map scrolling disabled ([MapView.java](https://github.com/react-native-maps/react-native-maps/blob/master/android/src/main/java/com/rnmaps/maps/MapView.java)). Two gaps remain. There is no drag-end event, so detect the end with `onTouchEnd` or a gesture-handler wrapper. Reliability on the iOS Google provider under the New Architecture is unconfirmed, so test on devices. Avoid the dedicated `react-native-maps-draw` library: it was last pushed in December 2023 and has open "Unable to draw" issues ([repo](https://github.com/dev-chief/react-native-maps-draw)). Expo's own `expo-maps` uses Apple Maps on iOS and exposes no screen-to-coordinate method ([Expo maps](https://docs.expo.dev/versions/latest/sdk/maps/)), so Expo apps should use react-native-maps ([Expo docs](https://docs.expo.dev/versions/latest/sdk/map-view/)).

**Flutter** has the sharpest edges. In google_maps_flutter 2.19.0, `getLatLng` returns a `Future` per point, specified "in screen pixels (not display pixels)" ([controller.dart](https://github.com/flutter/packages/blob/main/packages/google_maps_flutter/google_maps_flutter/lib/src/controller.dart)). The Android plugin passes the integer straight to `fromScreenLocation` without density scaling ([Convert.java](https://github.com/flutter/packages/blob/main/packages/google_maps_flutter/google_maps_flutter_android/android/src/main/java/io/flutter/plugins/googlemaps/Convert.java)), while iOS passes it to `coordinateForPoint`, which works in points ([FGMGoogleMapController.m](https://github.com/flutter/packages/blob/main/packages/google_maps_flutter/google_maps_flutter_ios/ios/google_maps_flutter_ios/Sources/google_maps_flutter_ios/FGMGoogleMapController.m)). **Multiply Flutter's logical offsets by `devicePixelRatio` on Android only.** Users have long reported this asymmetry; the issue was closed as not reproducible in 2021, yet the current source still shows it ([flutter#41653](https://github.com/flutter/flutter/issues/41653)). Also test gesture overlays on real iPhones: custom `GestureDetector` handling over `GoogleMap` worked on simulators but misbehaved on devices ([flutter#153469](https://github.com/flutter/flutter/issues/153469)). No maintained pub.dev package does freehand drawing on Google Maps. `google_maps_drawing_tools` is at 0.0.6 from an unverified uploader and documents no freehand mode ([pub.dev](https://pub.dev/packages/google_maps_drawing_tools)).

### Clean the shape before anything queries it

A raw finger stroke contains hundreds of points and often crosses itself, so normalize it once before rendering, storing or querying. Simplify it with Douglas-Peucker (Turf `simplify` or `PolyUtil.simplify`) down to tens of vertices ([Turf simplify](https://turfjs.org/docs/api/simplify)). Close the ring, because GeoJSON requires the first and last positions to match ([RFC 7946](https://datatracker.ietf.org/doc/html/rfc7946#section-3.1.6)). Force counterclockwise winding, which Places Aggregate requires ([RPC reference](https://developers.google.com/maps/documentation/places-aggregate/reference/rpc/google.maps.areainsights.v1)). Repair self-intersections with Turf `unkinkPolygon` ([Turf](https://turfjs.org/docs/api/unkinkPolygon)) or PostGIS `ST_MakeValid` ([PostGIS](https://postgis.net/docs/ST_MakeValid.html)). The DevFest talk shows why the repair matters: a figure-8 stroke makes different inside-tests disagree. The talk's fix unions the path with itself and normalizes lat/lng to a 0–10,000 range first, because a single-precision float "keeps about seven digits" and misplaces points near edges ([Speaker Deck](https://speakerdeck.com/stewemetal/paths-polygons-and-donuts-building-a-freehand-drawing-tool-for-maps-devfest-venezia-2026-edition)). On the web, `containsLocation` accepts only a `Polygon` or `Circle` and counts edge points as inside ([geometry guide](https://developers.google.com/maps/documentation/javascript/geometry)). Google does not document how it treats holes or multiple paths. Turf `booleanPointInPolygon` is the safer choice for unkinked MultiPolygons ([Turf](https://turfjs.org/docs/api/booleanPointInPolygon)). `spherical.computeArea` lets you reject accidental continent-sized lassos ([geometry reference](https://developers.google.com/maps/documentation/javascript/reference/geometry)).

## Google Places restricts only to circles and rectangles

Drawing is the easy part. Whether results stay inside the drawn shape depends on where the data lives, and **Google Places search endpoints do not accept a polygon**.

| Places API | Area it accepts | Result cap | Fit for a traced loop |
|---|---|---|---|
| Nearby Search (New) | Restriction: **circle only**, radius 0–50,000 m | **20**, no pagination | Cover the polygon with circles, then filter |
| Text Search (New) | Restriction: **rectangle only**; bias: circle or rectangle | 20 per page, **60 total** | Use the bounding box, then filter |
| Search Along Route | Encoded polyline (bias, not restriction) | Text Search caps | Poor: "may not return any results" when origin ≈ destination |
| Places Aggregate | Circle, region, or **custom polygon** | A count; Place IDs only if count ≤ 100 | Best fit for count badges |

Sources for the table: Text Search `locationRestriction` accepts only a rectangular viewport, and the API "returns a maximum of 60 results across all pages" ([Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search)). Nearby Search restricts to a circle and returns 1–20 results, with no page token ([Nearby Search](https://developers.google.com/maps/documentation/places/web-service/nearby-search)). Search Along Route biases toward a corridor and returns little for closed loops ([Search along route](https://developers.google.com/maps/documentation/places/web-service/search-along-route)). The **Places Aggregate API** lets you "define the area of interest using circles, regions, or custom polygons". It returns `INSIGHT_COUNT` or `INSIGHT_PLACES`, but Place IDs come back "only if the count is 100 or lower" ([Aggregate overview](https://developers.google.com/maps/documentation/places-aggregate/overview)). Its `customArea` takes one closed, counterclockwise exterior ring ([RPC reference](https://developers.google.com/maps/documentation/places-aggregate/reference/rpc/google.maps.areainsights.v1)). It bills under a single Pro-category SKU at 1,200 queries per minute ([Aggregate billing](https://developers.google.com/maps/documentation/places-aggregate/usage-and-billing)). That makes Aggregate the closest Google-native match to "show 210 / 349 inside my loop". Several things remain unknown: its per-request price is not listed on that page, and no vertex limit, self-intersection behaviour or Japan data-coverage statement was found.

Getting actual Places results inside a lasso means tiling the area and filtering. You compute the polygon's bounding box, cover it with circles or rectangles small enough that no tile hits the cap, subdivide any tile that returns exactly 20 (or 60), and then drop the results outside the polygon. Under the March 2025 pricing, the $200 monthly credit was replaced by free monthly caps per SKU: 10,000 Essentials, 5,000 Pro and 1,000 Enterprise events ([March 2025 changes](https://developers.google.com/maps/billing-and-pricing/march-2025)). **Nearby Search Pro and Text Search Pro cost $32 per 1,000 up to 100,000 requests**, and Enterprise costs $35. Nearby Search has no Essentials tier, and Text Search's Essentials tier returns IDs only ([pricing](https://developers.google.com/maps/billing-and-pricing/pricing)). Here is a rough estimate, not a Google figure. A lasso over dense central Tokyo containing about 350 matching places needs at least 18 Nearby requests with perfect packing, and 30–80 once circles overlap and spill outside the shape. Fifty requests come to about **$1.60 per search**, or roughly $1,600 for 1,000 searches a month once the free tier is used up. An IDs-only Text Search sweep is free, but every ID then needs a Place Details call ($5 per 1,000 after 10,000 free) to get coordinates for the inside test. Google does not explicitly confirm that each `pageToken` request bills as a separate event, though each one is a separate request.

The terms also rule out the obvious shortcut. "You must not pre-fetch, cache, or store Places API content beyond the allowed exceptions." Only **Place IDs may be stored indefinitely** ([Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)). So you cannot mirror Places into PostGIS and run polygon queries there. Places results shown on a map "must be shown on a Google Map" with the Google logo and any third-party attributions. Photos and reviews also require author credit ([Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)). Two related clauses are widely reported but were not verified in this research: a "No Use With Non-Google Maps" restriction and a 30-day allowance for caching lat/lng. Check both against the current [Maps Platform Terms](https://cloud.google.com/maps-platform/terms) before relying on them. The practical conclusion is that **radius is the shape Places supports natively**. If results come from Google, the "alternative" radius search is the primary path, and a lasso is a costly approximation layered on top of it.

## Your own listings turn polygon search into one query

A property app like the one in your example searches its own listings, and the constraints above disappear. Every major geo-capable store except Firestore filters by polygon natively. PostGIS is the simplest option: `WHERE ST_Intersects(location, ST_GeomFromGeoJSON($1)::geography)` with a GiST index. `ST_Within`/`ST_Contains` work on geometry columns only, while geography needs `ST_Intersects` or `ST_Covers` ([ST_Within](https://postgis.net/docs/ST_Within.html); [ST_Intersects](https://postgis.net/docs/ST_Intersects.html)). Supabase ships PostGIS as an extension ([Supabase](https://supabase.com/docs/guides/database/extensions/postgis)).

| Backend | Polygon filter | Coordinate order | Watch out for |
|---|---|---|---|
| PostGIS / Supabase | `ST_Intersects` / `ST_Within` | lng, lat (GeoJSON) | `ST_Within` is geometry-only |
| MongoDB | `$geoWithin` + GeoJSON `Polygon`/`MultiPolygon` | lng, lat | Results are unsorted; default CRS treats polygons larger than a hemisphere as their complement |
| Elasticsearch | `geo_shape` query on `geo_point` | lng, lat (GeoJSON/WKT) | `geo_polygon` deprecated since 7.12 |
| Algolia | `insidePolygon` | **lat, lng** (flat list) | Up to 10,000 pairs; `insideBoundingBox` overrides it; `aroundLatLng` ignored |
| Typesense | `filter_by=location:(lat, lng, …)` | **lat, lng** | Vertices must be in consistent CW/CCW order or the query errors |
| Meilisearch | `_geoPolygon([lat, lng], …)` | **lat, lng** | Only since v1.22.0 (Sept 2025); no antimeridian crossing |
| Firestore | None | — | Geohash ranges over a covering circle, then client-side filtering of paid false-positive reads |

Sources: [MongoDB $geoWithin](https://www.mongodb.com/docs/manual/reference/operator/query/geoWithin/); [Elasticsearch geo_polygon deprecation](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-geo-polygon-query); [Algolia insidePolygon](https://www.algolia.com/doc/api-reference/api-parameters/insidePolygon/); [Typesense GeoSearch](https://typesense.org/docs/latest/api/geosearch.html); [Meilisearch polygon filter](https://www.meilisearch.com/docs/capabilities/geo_search/how_to/filter_by_geo_polygon) and [v1.22 notes](https://www.meilisearch.com/blog/september-2025-updates); [Firestore geoqueries](https://firebase.google.com/docs/firestore/solutions/geoqueries). The most common silent bug is **coordinate order**. GeoJSON-family stores use `lng,lat`, while Algolia, Typesense and Meilisearch use `lat,lng`, so the normalizer should emit both orders. Firestore's documentation itself warns that geohash querying "is not exact" and that the extra reads add cost and latency ([Firestore](https://firebase.google.com/docs/firestore/solutions/geoqueries)). A Firebase app should sync listings into Typesense, Algolia or Meilisearch for this feature.

The clustered counts in your example come from one of two places. With a few thousand matching points or fewer, return the in-polygon listings and cluster them on the client. `@googlemaps/markerclusterer` uses a Supercluster-based algorithm by default and supports custom count renderers ([markerclusterer](https://github.com/googlemaps/js-markerclusterer); [Supercluster](https://github.com/mapbox/supercluster)). At larger scale, let the server return `{centroid, count}` cells. Elasticsearch's `geotile_grid` aggregation, filtered by the `geo_shape` polygon and paired with `geo_centroid`, does this ([geotile_grid](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-geotilegrid-aggregation); [geo_centroid](https://www.elastic.co/docs/reference/aggregations/search-aggregations-metrics-geocentroid-aggregation)), as does PostGIS `GROUP BY ST_SnapToGrid(...)` or `ST_ClusterDBSCAN` ([ST_SnapToGrid](https://postgis.net/docs/ST_SnapToGrid.html); [ST_ClusterDBSCAN](https://postgis.net/docs/ST_ClusterDBSCAN.html)). Badges anchored to wards or stations rather than pixels are simpler still: apply the polygon filter and facet on a `ward` or `station` attribute. Canary's version shows counts around the traced area, the user taps a count to open listings, and zooming in refines the counts ([Canary](https://note.com/canary_magazine/n/n734ea72f13a3)).

## Radius, stations and isochrones cover what tracing cannot

Every alternative you might offer can be built on Google Maps Platform, and each produces a shape that can feed the same backend query as the lasso.

| Pattern | Google building blocks | Strength | Weakness |
|---|---|---|---|
| Radius from current location | Browser/OS geolocation + `google.maps.Circle` (editable) | One tap; maps directly onto Nearby Search's circle | Needs location permission; useless for remote home-hunting; ignores rivers and rail lines |
| Radius from a chosen point | Long-press, Place Autocomplete, station picker | Works for "near my office"; keyboard-accessible | Same circle-shape limits; two steps |
| "Search this area" (viewport) | `Map.getBounds()` | Most familiar; matches Text Search's rectangle exactly | Area depends on zoom; users may not notice the restriction |
| Tap-to-place polygon | `google.maps.Polygon` (editable) or Terra Draw polygon mode | Precise; serves as the WCAG-compliant twin of tracing | Slower; small targets on phones |
| Predefined areas (市区町村, postal code, 駅, 沿線) | Data-driven styling boundaries; Region Lookup (Experimental) | Matches Japanese search habits; list UI is accessible | Administrative lines are not "north exit of the station" |
| Isochrone (駅徒歩10分圏) | **Isochrones API (Preview)**: walk/bike up to 120 min, drive up to 60 min | Matches user intent (time, not distance) | No transit; Preview API with no GA price |

The circle is the cheapest option and fits Japanese intent worst. SUUMO built なぞって探す in 2012 because users wanted areas like "only the north-exit side of a station" or "along a particular street" ([SUUMO release](https://digitalpr.jp/r/1733)). A circle cuts straight across the rail lines and rivers that users treat as hard edges. Radius still earns its place in two cases: for Places-backed results, because it is Google's native shape ([Nearby Search](https://developers.google.com/maps/documentation/places/web-service/nearby-search)), and as a one-tap "near me" entry. Draw it with an editable `google.maps.Circle` centred by geolocation ([Circle reference](https://developers.google.com/maps/documentation/javascript/reference/polygon#Circle); [geolocation example](https://developers.google.com/maps/documentation/javascript/examples/map-geolocation)). The selected-point variant is more useful for property search, where people often look far from where they are. SUUMO's web map search already combines Places Autocomplete with the Places Service to resolve typed places into coordinates ([Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)).

Two 2026-era Google features change the options. First, **Google now has an Isochrones API**, in pre-GA Preview. It supports WALK and BICYCLE up to 7,200 seconds and DRIVE and TWO_WHEELER up to 3,600 seconds, returns GeoJSON in lon,lat order, and does not support transit ([Isochrones FAQ](https://developers.google.com/maps/documentation/isochrones/faq)). Japan is in Tier 1 coverage ([coverage](https://developers.google.com/maps/documentation/isochrones/coverage)). A secondary source reports it is free during Preview, and no GA price has been announced ([afi.io](https://blog.afi.io/blog/mapping-travel-time-with-the-google-maps-isochrones-api/)). A "10 minutes' walk from this station" polygon feeds the same polygon query as a lasso, which makes it the strongest structured alternative for Japan. For commute-by-train search you still need TravelTime, which claims transit isochrones ([TravelTime](https://traveltime.com/blog/google-isochrones-api-vs-traveltime); Japan coverage unverified), or a station graph of your own. Mapbox is another fallback, capped at 60 minutes and four contours ([Mapbox Isochrone](https://docs.mapbox.com/api/navigation/isochrone/)). Hide the isochrone provider behind an interface so you can swap it if Google's terms change at GA. Second, data-driven styling boundaries cover Japan at country, prefecture, admin-level-2, locality and postal-code levels ([DDS coverage](https://developers.google.com/maps/documentation/javascript/dds-boundaries/coverage)). They only *style* Google's polygons, though, and you cannot query the geometry. "Search by ward" therefore works best as an attribute filter on listings that already carry a municipality code. Use DDS only to highlight the selection. The Region Lookup API that maps names to boundary IDs is still "Experimental (pre-GA)" ([Region Lookup](https://developers.google.com/maps/documentation/javascript/dds-boundaries/region-lookup)).

## Trace mode needs a button, a count, and an accessible twin

Shipped apps agree on the core interaction. SUUMO's 2012 launch flow was: pick an area or station, press the **なぞるボタン**, trace, and see pins ([SUUMO](https://digitalpr.jp/r/1733)). LIFULL HOME'S (2022) put the trace button at the bottom right of the map and let it combine with a flood-hazard overlay ([LIFULL](https://prtimes.jp/main/html/rd/p/000000241.000033058.html)). Canary (2023) uses a 👆 button at the bottom right, followed by tappable count bubbles ([Canary](https://note.com/canary_magazine/n/n734ea72f13a3)). Redfin puts a "Draw" button at the bottom of the map ([Redfin](https://support.redfin.com/hc/en-us/articles/360001432632-Searching-for-Homes)). **An explicit mode toggle is how every one of these apps resolves the draw-versus-pan conflict.** Scoping to a region first, as SUUMO and Canary do, also bounds the map and the query. Western portals add two refinements that Japanese apps do not appear to document. Rightmove's 2021 rebuild lets users edit or trim its predefined areas and syncs drawn areas across devices ([Rightmove](https://www.rightmove.co.uk/news/?p=80605)). Redfin ties drawn areas to saved-search alerts and offers up to five separate areas as an alternative to one shape ([Redfin multiple areas](https://support.redfin.com/hc/en-us/articles/360025724771-Multiple-Area-Search)).

The usage evidence is thin and comes only from the vendors themselves. Rightmove reported a **37% rise in bespoke drawn areas** in the month after its rebuild and about 250,000 areas drawn by late April 2021. It also said draw users "are more likely to be in the serious stage" ([Property Industry Eye](https://propertyindustryeye.com/?p=97652)). Recruit said SUUMO's map search "substantially improved" conversion compared with list search, without giving a number ([Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)). No NN/g or Baymard study comparing draw search with radius or list search was found. The Rightmove correlation could be selection bias, since serious buyers are the ones who find advanced tools. Read draw search as a high-intent, minority feature that belongs alongside saved searches and alerts, not as the main entry point. No public source documents how any of these apps handle auto-close, smoothing or self-intersection, so the following is engineering judgement. Close the loop when the finger lifts. Reject slivers with a "please trace again" message. Show a visible trail and start marker, because the finger hides the start of the stroke. Keep the drawn area as a removable filter chip that is combined (ANDed) with rent and layout filters. Never let a later pan silently replace the drawn area with a viewport search.

Accessibility pushes alternatives from nice-to-have toward required. WCAG 2.2 SC 2.5.1 (Level A) requires that path-based gestures can be operated with a single pointer without the path. W3C's own example of a path-based gesture is "drawing a specific shape". The only exemption is a gesture that is "essential", meaning the function "cannot be achieved in another way that would conform" ([W3C 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)). Restricting a search to an area clearly *can* be achieved another way, so freehand tracing is not essential. SC 2.5.7 (Level AA) adds dragging. Its W3C examples include a draggable map with arrow buttons, and a drag-drawn selection rectangle whose compliant alternative is "enable a selection mode and click or tap two corners" ([W3C 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)). Tap-to-place vertices are the direct analogue of that rectangle example. Station, ward and line lists, and radius or isochrone pickers driven by buttons, satisfy the criteria too. Editing vertices by dragging needs the same treatment. The trace button also needs an accessible name and keyboard access, and result counts should be announced after each change.

## Recommended approach: trace over your own index, radius over Google's

Choose the architecture by where the results come from, then build one shared polygon pipeline that every area mode uses.

| Result source | Lead search mode | How "inside the area" is enforced | Count badges |
|---|---|---|---|
| Your own listings (the なぞる app case) | Region first, then trace, with station/ward lists and walking isochrones beside it | Exact polygon query in PostGIS, Algolia, Typesense, Meilisearch, Elasticsearch or MongoDB | Server-side grid or ward facets, or client-side Supercluster |
| Google Places POIs | Radius (Nearby Search) or "search this area" (Text Search) | Native circle/rectangle; any lasso is approximated with a bounding box plus point-in-polygon on the top 20–60 | Places Aggregate `INSIGHT_COUNT` on the polygon |
| Both on one map | Same as own listings | Own data exact; Places capped and labeled "top results" | Separate counts; must be shown on a Google map with attribution |

For own data, which matches the Japanese example, ship trace mode behind an explicit button. Capture the stroke in screen space on an overlay with map gestures fully disabled. Convert to lat/lng once on lift. Then simplify, close, force counterclockwise winding and unkink. Send the GeoJSON to the backend combined (ANDed) with the other filters, and return clustered counts from the server. Platform choices follow from the first section. On desktop web, use Terra Draw's freehand mode with `drawInteraction: 'click-drag'` plus your own `gestureHandling: 'none'`. On mobile web, use the custom Pointer Events overlay unless Terra Draw passes testing on iOS Safari and Android Chrome. On Android, use a Compose `Canvas` overlay. On iOS, use a `UIView` overlay with a pan recognizer. In React Native, use `onPanDrag` with `scrollEnabled={false}`. In Flutter, use a `Listener` with `CustomPaint`, convert in batch with `Future.wait`, and apply the Android-only DPR correction. Store the simplified polygon with saved searches so it can drive alerts. Ship tap-to-place vertices and the station or ward list as the accessible equivalent. Instrument the share of sessions using each area mode, the zero-result rate and alert conversion, because no public benchmark tells you how much trace will be used.

For Google Places data, do not promise exhaustive results inside a lasso. Make radius from the current or a chosen location the primary mode, since it matches Nearby Search exactly. Use Places Aggregate for polygon counts, and label any lasso result list as "top results". Store only Place IDs, and display everything on a Google map with the required attribution.

## Conclusion

Google Maps itself rarely decides whether trace-to-search is feasible; the search index behind it does. The gesture is a solved, if hand-built, pattern on all five platforms. Polygon filtering, however, is first-class in your own geo index and nearly absent from Places. Google's 2026 moves point in the same direction. It removed its only drawing tool and redirected developers to unsupported third-party code, while it invests in *computed* areas (Isochrones) and *polygon counts* (Aggregate) rather than polygon search over Places. The design implication is to build the polygon pipeline (normalize, query, count, save) once and treat the finger trace as just one way to produce a shape. Radius circles, walking isochrones, ward boundaries and tap-placed vertices then reuse the same pipeline at almost no cost, and those same alternatives are what WCAG 2.2 requires.

Two risks remain open and should be tested before you commit. The first is touch reliability of freehand on mobile web, where even Terra Draw's documentation disclaims support. The second is Places Aggregate's unpublished pricing, vertex limits and Japan coverage, which decide whether Google-backed count badges are viable at all. Spike both first, and the rest of the build carries little technical risk.
