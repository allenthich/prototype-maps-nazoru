# Alternatives to freehand draw-to-search, real-world examples, and UX/accessibility gotchas

Scope note: These notes cover alternative area-selection patterns, shipped-product examples, UX pitfalls and accessibility. Freehand drawing implementation and backend geo-querying belong to other researchers. As of 2026-10-29. Some sources are old (SUUMO 2012, Rightmove 2010/2021, Redfin 2015); each is flagged where it matters.

## 1. Alternative area-selection patterns and the Google Maps Platform features that support them

### Takeaway
Every alternative the user named can be built on Google Maps Platform. Radius, viewport search, and tap-placed polygons use core Maps JS/SDK features. Predefined boundaries use data-driven styling (DDS), and Japan is covered for prefecture, admin-level-2, locality and postal code. The main 2026 change is that Google now has an **Isochrones API**. It is in Preview, covers Japan at Tier 1, and supports walk, bicycle, drive and two-wheeler, but **not transit**. A commute-by-train search in Japan therefore still needs a station-based or third-party approach. Separately, the Maps JS **Drawing Library was removed in May 2026**, and Google now points developers to Terra Draw.

### Cited Findings

**Comparison table.** Effort ratings are inferences, not sourced. Each "support" cell is backed by the findings below.

| # | Pattern | Google Maps Platform support | Implementation effort (inference) | Pros | Cons |

**Pattern 1–3: core Maps JS features**
- `google.maps.Circle` takes `center`, `radius` and `editable` options. With `editable: true` it shows drag handles for center and radius (API reference, not re-fetched this session) — [Maps JS reference: Circle](https://developers.google.com/maps/documentation/javascript/reference/polygon#Circle)
- Google documents a browser-geolocation example for centring the map on the user (not re-fetched this session) — [Maps JS geolocation example](https://developers.google.com/maps/documentation/javascript/examples/map-geolocation)
- `Map.getBounds()` returns the current viewport's lat/lng bounds, which is the basis of "Search this area" (not re-fetched this session) — [Maps JS reference: Map.getBounds](https://developers.google.com/maps/documentation/javascript/reference/map#Map.getBounds)
- SUUMO's map search (web) runs on Google Maps Platform and uses map display/scroll/zoom, markers, **Places Autocomplete Service** (input suggestions) and **Places Service** (to get lat/lng). Recruit said it chose Google Maps because users already know Google Maps. It also added area-name autocomplete so users don't have to scroll far to reach another area — [Recruit/SUUMO talk at a Google webinar, 2020-12-09 (slides 2020-12-24)](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)

**Pattern 4: tap-to-place polygons / drawing tooling**
- The Maps JavaScript API **Drawing Library was deprecated in August 2025 and is unavailable as of May 2026**. Google recommends **Terra Draw** as the replacement and provides a sample — [Google Maps JS Drawing Library page](https://developers.google.com/maps/documentation/javascript/drawinglayer)
- Rightmove's original Draw-a-Search (launched July 2010) worked by "connecting a series of points together to form an enclosed search shape", i.e. tap/click-placed vertices rather than freehand — [Property Reporter](https://www.propertyreporter.co.uk/property/rightmove-launches-draw-a-search.html); [Estate Agent Today](https://www.estateagenttoday.co.uk/news_features/Rightmove-introduces-new-drawing-search-tool)

**Pattern 5: predefined boundaries (Japan coverage)**
- Google's DDS boundary coverage table row for Japan reads "JP Japan ⬤ ⬤ ⬤ ⬤ ⬤ —". That means Country, Admin Area 1, Admin Area 2, **Postal code**, and **Locality** are available, and School district is not. SUBLOCALITY/NEIGHBORHOOD don't appear in the table. Google notes that postal-code coverage is more limited globally, and offers a region coverage viewer for per-polygon checks — [Google DDS boundaries coverage](https://developers.google.com/maps/documentation/javascript/dds-boundaries/coverage)
- DDS boundaries exist in the Maps JS API, Maps SDK for Android and Maps SDK for iOS — [JS overview](https://developers.google.com/maps/documentation/javascript/dds-boundaries/overview); [Android overview](https://developers.google.com/maps/documentation/android-sdk/dds-boundaries/overview); [iOS overview](https://developers.google.com/maps/documentation/ios-sdk/dds-boundaries/overview)
- Feature layers are turned on in a Cloud-based map style and need a vector Map ID. A boundary feature exposes only `placeId` and `featureType`, so names and geometry need a separate call (secondary source) — [afi.io blog on DDS boundaries](https://blog.afi.io/blog/google-maps-data-driven-styling-for-boundaries/)
- The **Region Lookup API is "Experimental (pre-GA)"**. It maps place names, addresses, lat/lng or place IDs to boundary place IDs for DDS. Supported types: country, administrative area level 1, level 2, postal code, locality. Lookups generally need a two-letter ISO-3166 `region_code`. The page has no deprecation notice — [Region Lookup API docs](https://developers.google.com/maps/documentation/javascript/dds-boundaries/region-lookup)
- Google's DDS launch post shows a sample polygon for a Japanese locality (Tadami) — [Google Maps Platform blog: data-driven styling](https://mapsplatform.google.com/resources/blog/introducing-data-driven-styling/)
- Japanese apps lean heavily on predefined areas. at home's two-person-living app lets users set the area by "2人の勤務先や『よく行く場所』" (both people's workplaces or frequent places), "駅や市区群を指定", or "地図をなぞって指定". at home notes this feature's screens were still in development — [at home app page](https://www.athome.co.jp/service/app/)

**Pattern 6: isochrone / travel-time**
- **Google Isochrones API** (pre-GA Preview). Inputs are an origin, a travel mode (DRIVE, TWO_WHEELER, BICYCLE, WALK) and a time limit. Max 3,600 s for DRIVE/TWO_WHEELER and 7,200 s for WALK/BICYCLE. TRAFFIC_AWARE routing works only for DRIVE and TWO_WHEELER. Output is GeoJSON (RFC 7946, **lon,lat order**, so some map SDKs need a swap). Origin snapping is ≤~200 m (WALK 150 m); a far-off origin returns NOT_FOUND. Ferries and water crossings are excluded. No transit — [Isochrones FAQ](https://developers.google.com/maps/documentation/isochrones/faq); [Key concepts](https://developers.google.com/maps/documentation/isochrones/key-concepts); [Create an isochrone](https://developers.google.com/maps/documentation/isochrones/create-isochrone)
- **Japan is covered at Tier 1** (the highest tier) in the Isochrones API coverage list. Google adds that "data quality can vary by country" — [Isochrones coverage](https://developers.google.com/maps/documentation/isochrones/coverage)
- Endpoint `POST https://isochrones.googleapis.com/v1/isochrones:generate`; "free to use while it's in Preview"; no GA price announced; multimodal/transit not supported (secondary source, 2026-07-26) — [afi.io: Google Maps Isochrones API](https://blog.afi.io/blog/mapping-travel-time-with-the-google-maps-isochrones-api/). Launch coverage from July 2026 — [Globema, 2026-07-20](https://google.globema.com/2026/07/20/google-maps-platform-isochrones-api/); [Localyse](https://localyse.eu/google-launches-isochrones-api/)
- **Flag:** any earlier claim that "Google doesn't offer isochrones" is outdated as of July 2026. Before mid-2026 the usual workaround was to approximate reachability with a Routes API `computeRouteMatrix` over a grid of points, since Routes API returns no polygons — [Routes API reference](https://developers.google.com/maps/documentation/routes/reference/rest)
- **Mapbox Isochrone API:** profiles driving-traffic, driving, walking, cycling; max 60 minutes; up to 4 contours; distance contours up to 100 km — [Mapbox Isochrone API docs](https://docs.mapbox.com/api/navigation/isochrone/)
- **TravelTime** says it returns isochrones for driving, **public transport**, cycling and walking, and that Google, HERE and Mapbox do not return transit isochrones. This is vendor marketing — [TravelTime: Google Isochrones API vs TravelTime](https://traveltime.com/blog/google-isochrones-api-vs-traveltime); [TravelTime isochrone docs](https://docs.traveltime.com/api/overview/isochrones). A 2021 TravelTime post claimed 100+ countries, 35 with full and 57 with partial transit coverage. That is outdated, and Japan is not confirmed — [TravelTime blog 2021](https://traveltime.com/blog/traveltime-adds-transport-data-coverage-for-12-countries)
- SUUMO's app lets users filter by "地図を指でなぞった範囲や通勤通学時間" (traced area or commute/school time) (app-review site, updated 2026-08-05) — [app-liv.jp SUUMO](https://app-liv.jp/9418/). In its 2020 talk, Recruit listed "目的地まで所要時間内に移動できる範囲の表示" (showing the reachable area within a time budget) as a future direction, citing 99.co and Trulia — [Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)

**Pattern 7: corridor / along-route**
- Places API (New) Text Search supports **Search Along Route** through `searchAlongRouteParameters.polyline.encodedPolyline`, with the polyline taken from the Routes API or encoded by hand. Results are "biased to the route" and chosen for minimal detour. The page doesn't say whether results can be strictly restricted. If origin and destination are the same or very close, the search may return nothing. It searches Google's Places data, not custom listings — [Search Along Route docs](https://developers.google.com/maps/documentation/places/web-service/search-along-route)

### Inferences
- **The best Google-native alternative set for a Japanese property app** is probably: (a) predefined areas (市区町村 / 駅 / 沿線) as the default and accessible path; (b) "Search this area" or viewport search with clustered counts; (c) walking isochrone from a chosen station or address ("駅徒歩10分圏") via the Google Isochrones API; and (d) freehand tracing as a power feature, with tap-to-place vertices as its accessible fallback.
- A static radius is the cheapest option but fits Japan poorly. Searches there are usually framed around stations and exits (SUUMO's 2012 rationale was "only the north-exit side of a station"; at home's copy is "駅の南側" (the south side of the station)). A circle crosses rail lines and rivers that users treat as hard boundaries. A walking isochrone fits that framing much better than a circle.
- Because the Google Isochrones API is Preview with no GA price, a production app should hide it behind an interface so it can swap to Mapbox, TravelTime, or self-hosted OpenRouteService or Valhalla. Transit/commute isochrones in Japan need TravelTime (Japan coverage unverified) or a station-graph approach (precomputed station-to-station times plus a walking buffer around each station). SUUMO's "通勤時間" search appears to be station-based rather than polygon-based, but that is unverified.
- DDS boundaries only *style* Google's polygons; the geometry isn't exposed for your own point-in-polygon queries. So "search by ward" is easiest as an attribute filter on listings (each listing already carries an address and municipality code) rather than a geometric query. Polygons, when needed, should come from open data such as MLIT 国土数値情報 行政区域 (not verified this session).
- How Google's LOCALITY / ADMINISTRATIVE_AREA_LEVEL_2 types map onto Japanese units is unverified. Tokyo's 23 special wards (特別区) and designated-city wards (政令指定都市の区) may not map to the same type. Check this with the region coverage viewer before relying on it.

### Gaps
- OpenRouteService and Valhalla isochrone limits and licensing were not fetched this session.
- TravelTime's current Japan transit coverage could not be confirmed.
- Google Isochrones GA date and pricing are not announced. "Free during Preview" comes only from a secondary source.
- No Google polygons exist for stations or rail lines. Station/line search needs your own data, and this was not researched here.
- Whether the Region Lookup API will stay Experimental or be replaced was not stated.

## 2. Real-world examples (Japanese and Western) of trace/draw and area search

### Takeaway
Freehand tracing is mainstream in Japanese property apps. **SUUMO introduced "なぞって探す" in July 2012** and claimed a first among property-search apps. LIFULL HOME'S, at home and Canary followed with near-identical designs: choose an area first, tap a dedicated trace (finger) button to enter draw mode, trace a closed shape, then see pins or count bubbles. In the West, Zillow, Redfin, Rightmove and idealista all ship draw search, and Rightmove and Redfin tie it to saved searches and alerts. I found no documented case of a major portal *removing* draw search.

### Cited Findings

**Japan**
- **SUUMO (Recruit), iPhone, 2012-07-02.** Billed as "不動産検索アプリ初「なぞって探す」機能" (first trace-to-search in a property app); rentals only at launch; iOS 4.0+. Flow: on the 借りる (rent) top screen tap the "なぞって探す" menu, choose an area or station so a map appears, press the **"なぞるボタン"** (trace button), trace the search boundary with a finger, and matching properties appear as pins. Rationale: users wanted narrower areas such as "only the north-exit side of a station" or "along a particular street". No usage stats given — [SUUMO press release, digitalpr.jp](https://digitalpr.jp/r/1733). An Android version followed — [SUUMO Android press release](https://digitalpr.jp/r/1869)
- SUUMO's app still offers trace search plus commute/school-time search in 2026, per an app-review site (last updated 2026-08-05; not official) — [app-liv.jp](https://app-liv.jp/9418/). App Store listing — [SUUMO App Store (JP)](https://apps.apple.com/jp/app/%E8%B3%83%E8%B2%B8-%E5%A3%B2%E8%B2%B7%E7%89%A9%E4%BB%B6%E6%A4%9C%E7%B4%A2-suumo-%E3%82%B9%E3%83%BC%E3%83%A2-%E3%81%A7%E3%81%8A%E9%83%A8%E5%B1%8B%E6%8E%A2%E3%81%97/id359578668)
- The SUUMO 2020 slides name the app feature 「なぞって検索」 and the smartphone-web counterpart 「地図検索」 (map search). Web map search runs on Google Maps Platform and uses React/SPA for performance. Property icons are colour-coded by type and made more saturated than Google's POI icons. Previous search conditions are restored on revisit — [Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)
- **LIFULL HOME'S, iPhone/iPad, 2022-03-30.** Choose 借りる/買う (rent/buy) and an area, open map results, and tap the **なぞるボタン at the bottom right** of the map to enter trace mode. Tracing an area by finger filters listings to that range (examples: "near the east exit of a station", "near a park"). It can be combined with a **flood hazard-map overlay** (浸水ボタン, top right), which uses a colour-blind-friendly display that LIFULL says is patent pending. It covers rentals and sales nationwide and was billed as the first major Japanese portal app to offer both features. No usage stats given — [LIFULL PR Times release, 2022-03-31](https://prtimes.jp/main/html/rd/p/000000241.000033058.html)
- **at home:** marketing copy 「地図を囲むだけ検索」 ("just circle the map"): "『駅の南側』『商店街の周辺』など、地図を指でなぞるだけで、探したい場所をピンポイントで設定" ("the south side of the station", "around the shopping street" — pinpoint the area just by tracing the map with a finger). The two-person-living app also lets users set the area from both partners' workplaces, from stations/municipalities, or by tracing — [at home app page](https://www.athome.co.jp/service/app/)
- **Canary (カナリー), 2023-06-08.** Flow: search tab → choose prefecture → 「なぞって」 button → press the 👆 button at the bottom right → circle the area with a finger → **tap the number (property count) shown around the area**. Zooming in refines to a finer area. Results then appear in a swipeable bottom card carousel that can switch to a list. Rationale: lets people who are weak at geography search intuitively. Claimed benefits (projections, no data): more exposure for listings and a broader audience (families who care about locality, beyond the core 20s–30s women) — [Canary note article](https://note.com/canary_magazine/n/n734ea72f13a3)
- Japanese rental-map-search comparison article (37 sites) — [sumai-kyokasho.net](https://sumai-kyokasho.net/search-rental-by-map/) (not fetched; listed for the writer's follow-up)

**Western**
- **Rightmove (UK):** "Draw-a-Search" launched July 2010 by joining points into an enclosed shape — [Property Reporter](https://www.propertyreporter.co.uk/property/rightmove-launches-draw-a-search.html). In 2021 it was "completely rebuilt and integrated into the property search flow". One drawn area can span several towns, cities or boroughs. Users can **edit Rightmove's predefined location areas** (including excluding parts), and drawn areas sync across devices when signed in — [Rightmove news, 2021-03-23](https://www.rightmove.co.uk/news/?p=80605); [Property Industry Eye, 2021-04-27](https://propertyindustryeye.com/?p=97652)
- **Redfin:** the website has a "Draw" button at the bottom of the map to "draw any shape", and "Save Search" for email alerts. As an alternative to drawing, users can add **up to five locations at once** (Multiple Area Search) — [Redfin support: Searching for Homes](https://support.redfin.com/hc/en-us/articles/360001432632-Searching-for-Homes); [Redfin support: Multiple Area Search](https://support.redfin.com/hc/en-us/articles/360025724771-Multiple-Area-Search). The iPhone app got "Draw Your Own Search" in March 2015 ("draw a line around where you want to search for homes"), and Redfin.com got it by August 2016. The rationale was exact areas rather than neighbourhoods or ZIP codes, plus alerts in competitive markets — [Redfin blog, 2015-03-19 (updated 2020)](https://redfin.com/blog/2015/03/draw-your-own-search-on-the-redfin-iphone-app.html)
- **Zillow:** the help centre describes clicking the draw icon, outlining the area and clicking Apply. The iPhone help page describes "Draw" pulling in all properties within the drawn boundary. I saw these only in search snippets: the iPhone page returned 403 when fetched, and the article is about 1,000 days old, so it may be outdated — [Zillow help: How do I search for properties](https://zillow.zendesk.com/hc/en-us/articles/227953268-How-do-I-search-for-properties); [Zillow help: iPhone search](https://zillow.zendesk.com/hc/en-us/articles/360000808587-How-do-I-search-for-homes-on-the-Zillow-mobile-app-iPhone)
- **idealista (Spain/Portugal/Italy):** the App Store listing says users open the map and "trace the area where you'd like to live with your finger" and all listings appear instantly with prices — [idealista App Store](https://apps.apple.com/app/idealista-com/id465958311)
- **Akiya Japan** (English-language Japan vacant-house portal) has a subscriber-only "Draw Tool" (article dated 2026-07-01) — [Akiya Japan: Using your Draw Tool](https://www.akiyajapan.com/articles/feature-using-your-draw-tool)
- A US vendor blog says Zillow, Redfin and Rightmove "did not make maps optional by accident" and that map views help users understand trade-offs faster. This is opinion without data — [Raw Studio](https://raw.studio/blog/using-maps-as-the-core-ux-in-real-estate-platforms/)

### Inferences
- The Japanese pattern is remarkably consistent across SUUMO (2012), LIFULL (2022) and Canary (2023): **(1) choose a region first, (2) explicit trace-mode button with a finger icon (Canary and LIFULL put it bottom-right), (3) trace one closed loop, (4) show results as pins or count bubbles plus a list toggle**. Copying these conventions lowers learning cost for Japanese users who already know SUUMO and HOME'S.
- Western portals tie drawing to *saved searches and alerts* (Rightmove, Redfin), and Rightmove generalised it into *editing predefined areas*. That hybrid (start from a ward, then trim or extend) is a strong pattern Japanese apps don't appear to document.
- LIFULL pairing trace search with a hazard overlay suggests area search is valued as a way to *combine spatial layers* (flood zones, school districts), not only to restrict a list.

### Gaps
- **No documented removals found.** I found no source showing that Zillow, Redfin, Trulia, SUUMO or others removed draw search, or why. Absence of evidence is not proof.
- **CHINTAI**: not verified whether its app has a trace feature. **Realtor.com**: draw tool not verified this session.
- Fine details such as auto-close, smoothing, redraw and multiple shapes were not documented in any official Japanese source. The ieagent.jp SUUMO guide ([link](https://ieagent.jp/blog/chie/suumo-nazottesagasu-541442)) returned 403.
- None of the Japanese press releases include usage numbers.

## 3. UX gotchas (gesture conflicts, closing/smoothing, editing, filters, counts, small screens, saving)

### Takeaway
Every shipped app I found solves the draw-vs-pan conflict the same way: an **explicit draw-mode button** (SUUMO's なぞるボタン, LIFULL's bottom-right button, Canary's 👆 button, Redfin/Zillow "Draw"). Count feedback (Canary's tappable count bubbles), an apply step (Zillow), editing or trimming predefined areas (Rightmove), and save-for-alerts (Rightmove, Redfin) are the documented supporting patterns. Smoothing, auto-close and self-intersection handling are not documented publicly. The guidance below on those is engineering inference.

### Cited Findings
- **Explicit mode toggle.** SUUMO: press the なぞるボタン, then trace — [SUUMO release](https://digitalpr.jp/r/1733). LIFULL: なぞるボタン at bottom right enters trace mode — [LIFULL release](https://prtimes.jp/main/html/rd/p/000000241.000033058.html). Canary: 「なぞって」 then the 👆 button at bottom right — [Canary](https://note.com/canary_magazine/n/n734ea72f13a3). Redfin web: "Draw" button at the bottom of the map — [Redfin support](https://support.redfin.com/hc/en-us/articles/360001432632-Searching-for-Homes)
- **Region-first scoping.** SUUMO and Canary make the user pick an area, station or prefecture *before* tracing, which bounds the map and the query — [SUUMO](https://digitalpr.jp/r/1733); [Canary](https://note.com/canary_magazine/n/n734ea72f13a3)
- **Counts before results.** Canary shows property counts as numbers around the traced area. The user taps a count to see listings, and zooming in gives finer-grained counts — [Canary](https://note.com/canary_magazine/n/n734ea72f13a3)
- **Apply step.** Zillow: draw → outline → "Apply" (help snippet; possibly dated) — [Zillow help](https://zillow.zendesk.com/hc/en-us/articles/227953268-How-do-I-search-for-properties)
- **Edit, combine and exclude.** Rightmove lets one drawn area span several towns, lets users edit predefined areas, and lets them exclude parts — [Rightmove 2021](https://www.rightmove.co.uk/news/?p=80605). Redfin offers up to five separate locations as an alternative to one shape — [Redfin Multiple Area Search](https://support.redfin.com/hc/en-us/articles/360025724771-Multiple-Area-Search)
- **Save for alerts and cross-device.** Rightmove drawn areas sync across devices when signed in — [Rightmove 2021](https://www.rightmove.co.uk/news/?p=80605). Rightmove's 2021 rebuild encouraged more users "to choose their preferred area and sign up for real-time alerts" — [Property Industry Eye](https://propertyindustryeye.com/?p=97652). Redfin: "Save Search" for email alerts — [Redfin support](https://support.redfin.com/hc/en-us/articles/360001432632-Searching-for-Homes). Redfin's 2015 rationale highlighted alerts for listings, price drops and sales in the drawn area — [Redfin blog](https://redfin.com/blog/2015/03/draw-your-own-search-on-the-redfin-iphone-app.html)
- **Combining with filters and layers.** LIFULL lets the flood-hazard overlay stay on while the trace filter is active — [LIFULL release](https://prtimes.jp/main/html/rd/p/000000241.000033058.html)
- **Restore state.** SUUMO restores the previous search conditions on revisit — [Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)
- **Small screens.** Mobile maps are constrained by "small screen real estate and a variety of screen sizes" (academic, general) — [run.unl.pt thesis](https://run.unl.pt/handle/10362/33716)

### Inferences
These are engineering or design recommendations, not sourced.
- **Draw vs. pan:** In draw mode, take over one-finger drag for the stroke. Either disable map gestures, or allow two-finger pan and pinch-zoom while drawing (on Google Maps JS, `gestureHandling` and `draggable` options control this). Leave draw mode automatically after the stroke ends, and give an obvious cancel/exit. Show a mode indicator (tinted overlay, hint text such as 「指で囲んでください」 ("circle the area with your finger")) so a stray swipe doesn't pan or draw unexpectedly.
- **Auto-close:** Close the path on touch-up by joining the last point to the first. Reject strokes that are too short or too small (for example, an enclosed area below a minimum, or fewer than N points) with a gentle "もう一度なぞってください" ("please trace again") rather than silently searching a sliver.
- **Smoothing and simplification:** Raw touch strokes have hundreds of points. Simplify them (for example, Douglas–Peucker) before rendering, saving to a URL or sending to the backend, to keep query cost and URL length bounded.
- **Self-intersections:** Figure-8 traces give invalid polygons. Either take the convex hull or outer ring, or repair with buffer(0)/unkink and treat each loop as a separate area. Tell the user if the shape was changed.
- **Editing:** After drawing, offer "なぞり直す" (redraw) and "クリア" (clear). Optionally convert the shape to an editable polygon with draggable vertices, with a tap-select-and-nudge or delete-vertex alternative for accessibility (see section 4). Supporting multiple shapes (Redfin up to 5 areas; Rightmove multi-borough) is a nice-to-have.
- **Filters:** The drawn area should AND with the other filters (rent, layout, walking minutes to station) and be shown as a removable chip, e.g. 「なぞったエリア ×」, alongside the other conditions.
- **Counts:** Show the live result count while or just after drawing (Canary-style bubbles, or a "120件" badge on the shape), and show "0件" states with suggestions (expand area, relax filters).
- **Fat fingers:** A finger hides the stroke start. Draw a visible trail and a start-point marker, and make the snap-to-close radius generous (for example ~20–30 px). Keep the draw/clear/apply buttons at least 44 pt (Apple HIG) / 48 dp (Material); the 2.2 AA floor is 24×24 CSS px (not fetched).
- **Viewport interaction:** After a traced search, panning shouldn't silently replace the traced area with a viewport search. Rightmove's 2021 rebuild and the "search as I move the map" pattern both imply an explicit choice between a drawn area and the viewport.
- **Saving:** Store simplified polygons server-side, tied to saved searches and push/email alerts, as the Rightmove and Redfin evidence shows this drives engagement.

### Gaps
- No official source documents auto-close, smoothing, self-intersection handling, or two-finger-pan-while-drawing in SUUMO, LIFULL, at home, Canary, Zillow or Redfin.
- No published A/B results on explicit mode toggles vs. modeless drawing were found.

## 4. Accessibility: WCAG 2.2 SC 2.5.1 and 2.5.7, and accessible alternatives

### Takeaway
Freehand trace-to-search is a **path-based gesture** (SC 2.5.1: "drawing a specific shape" is the W3C's own example), and it also involves dragging (SC 2.5.7). Both criteria require a single-pointer alternative unless the gesture is "essential". It is essential only when the function "cannot be achieved in another way that would conform". Restricting search to an area *can* be done another way (tap-placed vertices, radius, area lists), so **draw-to-search almost certainly needs a non-path alternative to conform at Level A/AA**. W3C's own two-corner selection-rectangle example is a close template.

### Cited Findings
- **SC 2.5.1 Pointer Gestures (Level A)** reads: "All functionality that uses multipoint or path-based gestures for operation can be operated with a single pointer without a path-based gesture, unless a multipoint or path-based gesture is essential." A path-based gesture is one "where the movement of the pointer along a specific path matters" (for example swiping, or "drawing a specific shape"). Signatures may be "inherently path-based". Map example: pinch-zoom is satisfied by +/- buttons — [W3C Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)
- **Essential** means "if removed, would fundamentally change the information or functionality of the content, **and** information and functionality cannot be achieved in another way that would conform" — [W3C Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html); [W3C Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- **SC 2.5.7 Dragging Movements (Level AA, new in 2.2)** reads: "All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging, unless dragging is essential or the functionality is determined by the user agent and not modified by the author." W3C examples: (a) a **map** that can be dragged also has up/down/left/right buttons, which is compliant; (b) drawing a **selection rectangle** by dragging, with a non-drag alternative of "enable a selection mode and click or tap two corners"; (c) drawing connecting lines by dragging, with an alternative of tapping item A then item B. An action can fail both 2.5.1 and 2.5.7 — [W3C Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- W3C technique **G219** ("Ensuring that an alternative is available for dragging movements that operate on content") — [W3C G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219.html)

### Inferences
- **Conformance reading:** Freehand tracing probably fails 2.5.1 and 2.5.7 unless the same "restrict search to an area" function is available through single-pointer, non-drag means. Accepted alternatives in descending fidelity:
  1. **Tap-to-place vertices** (tap points, then tap "close" or the first point). This is a direct analogue of W3C's two-corner rectangle example.
  2. **Predefined area lists** (市区町村, 駅, 沿線, postal code) with checkboxes. These are also keyboard and screen-reader friendly.
  3. **Radius or isochrone from a point** chosen by address or station autocomplete, with a radius or minutes picker implemented as buttons or a select, not drag-only.
  4. Viewport search, with the map panned and zoomed by buttons.
- Editing a drawn polygon by dragging vertices also needs a non-drag alternative, such as select vertex → arrow buttons, or delete vertex.
- **Beyond 2.5.x:** draw mode needs a keyboard-reachable entry and exit (2.1.1 Keyboard, Level A) and accessible names for icon-only buttons (Canary's 👆 button; LIFULL/SUUMO finger icons). The result count should be announced through a live region after a trace or area change. Use 2.5.8 Target Size (Minimum, AA, 24×24 CSS px) for the draw, clear and apply controls. These criteria were not fetched this session.
- **Japan context (unverified this session):** Japan's JIS X 8341-3:2016 tracks WCAG 2.0, which predates 2.5.x. So 2.5.1/2.5.7 are best-practice rather than JIS-mandated in Japan, but they apply to any WCAG 2.1/2.2 target (EU EAA, US ADA litigation, App Store expectations). Verify before stating legally.

### Gaps
- No W3C document addresses freehand map-area drawing specifically. The "not essential" conclusion is an inference from the definitions and the W3C rectangle example.
- No accessibility audit or statement from SUUMO, LIFULL, Zillow, Redfin or Rightmove on their draw features was found.

## 5. Data on usage and effectiveness of draw search vs. radius or area lists

### Takeaway
Public quantitative evidence is thin and vendor-reported. Rightmove reported a **37% rise in bespoke drawn areas** in the month after its 2021 rebuild, **~250,000 areas drawn** by late April 2021, and that draw users are "more likely to be in the serious stage". Recruit reported that SUUMO's map search **substantially improved conversion vs. list search**, with no figure given. I found no NN/g or Baymard research comparing draw-search with radius or area-list search.

### Cited Findings
- Rightmove: bespoke search areas rose **37%** in the month after the rebuilt draw tool launched (March 2021). A **quarter of a million areas** had been drawn so far in 2021. More than **78 million property alerts** went out in March (all alert types, not only draw) — [Property Industry Eye, 2021-04-27](https://propertyindustryeye.com/?p=97652)
- Rightmove CPTO Tarah Lourens: "Our analysis shows that home-hunters using draw-a-search are more likely to be in the serious stage", and the rebuild encouraged more users to pick a preferred area and sign up for real-time alerts — [Property Industry Eye](https://propertyindustryeye.com/?p=97652)
- Rightmove's 2010 launch also reportedly drove traffic gains (headline only; not fetched) — [Computing.co.uk](https://www.computing.co.uk/news/2107832/rightmove-boosts-traffic-google-maps-feature)
- SUUMO/Recruit (2020): map-based search CVR "大幅に改善" (substantially improved) vs. list-based search, with no number disclosed. A qualitative study of 4 users considering a move found "地図だと、物件の位置関係が直感的に理解できる" (on a map, the positional relationships between properties are intuitive). Validation focused on mid-consideration users because it was closest to conversion — [Recruit/SUUMO slides](https://speakerdeck.com/recruitengineers/suumo-sumo-gati-gong-suru-di-tu-karatan-su-zhu-maitan-siti-yan-falsexin-tanaqu-rizu-mi)
- Canary's stated expected effects of なぞって検索 (more listing exposure, broader user base) are projections, not measured outcomes — [Canary note](https://note.com/canary_magazine/n/n734ea72f13a3)
- Searches for NN/g and Baymard research on map "search this area" or draw search returned no relevant articles. Only vendor blogs and academic heuristics papers turned up, e.g. 12 usability heuristics for interactive web maps (2024) — [SciTePress 2024](https://www.scitepress.org/publishedPapers/2024/126913/pdf/index.html)

### Inferences
- The available evidence suggests draw search is a **high-intent, minority** feature. It correlates with serious buyers and with alert sign-ups, which supports pairing it with saved-search alerts rather than treating it as the main entry point. The correlation could be selection bias (serious users discover advanced tools), not causation.
- Since none of the Japanese portals publish usage share for なぞって vs. 駅/エリア search, an MVP should instrument its own funnel: share of sessions using each area mode, results-per-search, zero-result rate, and save/alert conversion.

### Gaps
- No public usage share for draw search vs. radius vs. area lists at any portal.
- No NN/g or Baymard study on this topic was found.
- The Rightmove figures are 2021, company-reported and unaudited. No newer (2024–2026) figures were found.
- No Japanese portal discloses なぞって usage metrics.
